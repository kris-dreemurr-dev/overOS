# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

overOS: a from-scratch x86_64 bare-metal OS in C99 + NASM, no libc anywhere (kernel, modules or programs). Comments, log strings and the readme are in Russian. `readme.md` has the full boot pipeline, memory layout and a (partly outdated) syscall table.

## Commands

Host deps: gcc, nasm, binutils (ld/objcopy/readelf/nm), mtools, dosfstools, python3, qemu-system-x86.

- `make`: builds the full disk image `build/os.img` (MBR + stage2 + FAT32 partition containing kernel, modules, programs, DE apps).
- `make run`: build + boot in QEMU (KVM, EHCI USB storage, intel-hda audio, serial on stdio, guest errors in `qemu_error.log`).
- `make run-debug`: same with TCG and `-d int` (interrupt trace into `qemu_error.log`), for triple faults and #PF debugging.
- `make modules` / `make libs` / `make progs`: only `.sys` / `.ll` / `src/programs/*.prg`. `make libs` builds the real FFmpeg the first time it runs (half a minute; the source archive is downloaded once into `src/libs/ffmpeg/dist` unless `FFMPEG_TARBALL` points at one). 
- `make install`: interactive installer `tools/installer_gui.py` (sudo, writes to real USB sticks). `make install-modules DEV=/dev/sdX` updates files on an already flashed stick. Both touch real block devices; don't run them unless asked.
- Image tunables: `PART_SIZE_MB`, `INSTALL_MODULES`, `INSTALL_PROGS`, `WITH_DOOM`, `WITH_QUAKE`, `WITH_DESKTOP`, and the accounts `ROOT_PASS` / `OS_USER` / `OS_PASS` (`tools/mkusers.py` generates `/etc`). By default `OS_USER` is empty: the image contains only root, `/etc/oobe` is `0`, and first boot runs the setup wizard (OOBE). `make OS_USER=kris OS_PASS=...` skips it and makes that user an administrator (in `wheel`). With an empty `ROOT_PASS`, root is locked (`!` in shadow), as on Ubuntu/CachyOS.
- **The build is parallel by default** (`MAKEFLAGS += -j$(nproc)` unless a `-j` is given; `make -j1` still works for reading errors in order). Each desktop app builds in its own `build/` directory, so the sub-makes do not collide. Measured on 6 cores: no-op 0.03 s, one kernel `.c` 1 s including the whole image, a header used by half the kernel 1.9 s, `desktop.c` 0.7 s; from scratch 89 s, almost all of it FFmpeg (already parallel inside, so `-j` alone saves only ~10% there — 98 s serial).
- **What made it feel slow was the installer**: `tools/installer_gui.py` started every install with `make clean` (deleting the built FFmpeg) and then built everything **as root** in one thread, which also left `build/` owned by root so the next normal build failed. It now builds through `make_cmd()` as `SUDO_USER` with `-j`, and never cleans: `build/.accounts` records the accounts **and** `PART_SIZE_MB`, `WITH_DOOM`, `WITH_QUAKE`, `WITH_DESKTOP`, `INSTALL_MODULES`, `INSTALL_PROGS`, so changing any of them repacks the partition by itself.
- If `build/` or the program build dirs are still owned by root (from an older `sudo make install`), the user build fails with "Отказано в доступе". Fix: `sudo chown -R $USER build src/files/progs` — cheaper than deleting `build/`, which costs a full FFmpeg rebuild.
- Kernel, module and program objects are compiled with `-MMD -MP` and the generated `.d` files are `-include`d. Before that the rule was `$(BUILD_DIR)/%.o: $(SRC_DIR)/%.c` with **no header prerequisites**, so editing a struct in a header (e.g. `task_t` in sched.h) rebuilt only the edited `.c` and left the rest of the kernel compiled against the old field offsets — processes started with garbage registers and it looked like a random BSOD. If you ever see that signature, check for stale objects first.
- `make compile-commands` writes `compile_commands.json` (gitignored) for clangd / the VS Code C/C++ extension, so the editor knows the `-I` paths and freestanding flags. Without it, `#include "ui.h"` and friends show up as unresolved even though the build is fine. Re-run it after adding a source directory. `clangd --check=<file>` is a quick way to verify; its "tweak: ... FAIL" lines are clangd's own refactoring-hint bugs, not code diagnostics.
- Headless smoke test: run QEMU with `-display none -monitor unix:<sock>,server,nowait` and `snapshot=on` on a copy of `build/os.img`, then drive it with the monitor commands `sendkey`, `mouse_move` / `mouse_button` and `screendump`. The first screen is the VBE mode menu, so send `ret` first. Games/demos that blit frames ignore Ctrl+C; they exit with Esc.

**Build gotchas** (all three bit us once, so don't undo them):
- A program's own `.ll` heap (`LL_ARENA_KB`) is compiled into `build/ll/cxxrt.o`, which now depends on the app's makefile. It did not before: raising overCraft's arena from 28 to 64 MB changed nothing in the image, and maximizing the game at 1600x900 or more still died with exit code 12 (cxxrt's out-of-memory exit: 12.8 MB triangle buffer + depth + the dynamic-resolution colour buffer + the holes left by the smaller ones). Exit code 12 from a C++ program means "check the arena first".
- The app dirs are rebuilt through `FORCE` prerequisites, so top-level `make` always descends into them. Their own makefiles list every header as a prerequisite — without that, editing `window.h` left stale objects compiled against the old struct layout, and fields silently read at the wrong offsets.
- `build/.accounts` records `ROOT_PASS|OS_USER|OS_PASS`, and the FAT32 partition depends on it. Otherwise changing the accounts left the previous build's `/etc` in the image.
- `.DEFAULT_GOAL := all` is set explicitly, because service rules are declared before `all:` and the first rule would otherwise become the default goal.

## Architecture

### Binary kinds
Three executable formats, all produced from ELF by Python tools in `tools/`:

| Kind | Ring | Source | Link | Packer |
|---|---|---|---|---|
| `kernel.bin` | 0 | `src/kernel`, `drivers`, `fs`, `memory`, `asm` | `linker.ld`, higher half `0xFFFFFFFF80000000`, flat binary | — |
| `.sys` modules (SREL, magic `DSYS`) | 0 | `src/modules/<name>_module.c` | `src/modules/module.ld`, PIE with `--emit-relocs` | `tools/elf2sys.py` |
| `.prg` programs (DPRG header) | 3 | `src/programs/*.c` or `src/files/progs/*` | `user.ld` / per-app `.ld`, base `0x4000000000`, `-mcmodel=large` | `tools/elf2prg.py` (`--desktop` sets `PRG_FLAG_DESKTOP`) |
| `.ll` shared libraries (DLIB, "linked library") | 3 | `src/libs/*.c` | `src/libs/lib.ld`, PIE base 0 with `--emit-relocs` | `tools/elf2ll.py` |

- **Kernel link is two-pass:** `kernel_stage1.elf` → `nm` → generated `build/ksyms.c` (symbol table `auto_ksyms`) → final `kernel.bin`. New kernel `.c` files must be added to `C_SRC` in the Makefile by hand (there is no wildcard).
- **Modules** get kernel services only through the `devos_api_t` function-pointer table (`src/drivers/api.h`) passed to `driver_entry`. They are compiled with `-mgeneral-regs-only -mno-sse`; no floating point in modules. To add a module, append its name to `MODULES`. Multi-file modules need an explicit rule (see `redactor.sys`).
- **Programs** talk to the kernel only via `int 0x80`: RAX = number, RBX/RCX/RDX = args, uint64 return. `src/libs/common/ovos.h` is the single wrapper header for all of userspace — console programs, DOOM/Quake (`-I../../../lib` in their makefiles) and DE apps include it instead of pasting their own inline asm.
- No libc: GCC can still emit `memcpy`/`memset` for struct copies and loops, which then fail to link. The kernel uses `rep movsb`/`stosb` helpers instead (see `wm_copy`/`wm_zero` in `user_mode.c`).

### Physical and virtual memory
- **RAM size comes from the BIOS, not from a constant.** stage2 asks INT 15h/E820 before leaving real mode and leaves the map at `0x5800` (count) / `0x5810` (entries of 24 bytes), which `kernel_main` reads through `e820_entry_t`. Only regions of type 1 are handed to the PMM, so ACPI/NVS and the PCI hole stay reserved. It used to be `pmm_init(512 MB)` hard-coded: a laptop with 8 GB used a sixteenth of its memory. Capped at 32 GB (the bitmap at phys `0x1F00000` is one megabyte).
- **`PHYS_TO_VIRT` is a direct map of all physical memory at `0xFFFF8000'00000000`** (`DMAP_BASE`, PML4[256]), built in `vmm_init` from static 2 MiB page tables in the kernel's `.bss` (`dmap_pdpt`/`dmap_pd`, up to 64 GB). The old window at `0xFFFFFFFF80000000` only covered the first gigabyte, which is why the kernel could not touch a page above it. The kernel image keeps living at `KERNEL_VIRT_BASE`; `virt_to_phys()` in vmm.h translates back from either range, and the four drivers that did the subtraction by hand (EHCI, ethernet, HDA, kernel stacks) go through it. Every address space clones `kernel_pml4[256]`, and `vmm_destroy_address_space`/`vmm_clone_address_space` skip index 256 — it is shared, not the process's.
- **`pmm_alloc_page` keeps a rolling hint** and skips whole `0xFF` bytes. It used to scan the bitmap from bit 1 on every call, so allocating a 50 MB process meant 12800 passes over the whole bitmap — that was the real reason opening an image or a video stalled the desktop. With 16 GB the bitmap is four million bits and the old loop would have been hopeless.
- `pmm_alloc_pages` (contiguous) allocates **below 4 GB only**: those are the DMA buffers (USB, ethernet, audio rings) and the 32-bit controllers cannot address higher.
- `pmm_get_total_blocks()`/`pmm_get_used_blocks()` count only pages the BIOS called usable, so the gigabyte-wide PCI hole is not reported as "occupied". Syscall **128 `sys_meminfo`** gives total/used bytes (`free` in the shell, "О системе" in overSettings).

### CPU identification and frequency (`src/kernel/cpu.c`)
- The kernel used to know nothing about the CPU beyond the CPUID brand string and never touched frequency: the multiplier stayed wherever firmware left it. `cpu_init()` (called from `kernel_main` **after** `init_user_mode`, see below) reads the topology and the ratios, clears the turbo **disable** bit (Intel `MISC_ENABLE` bit 38, AMD `HWCR` bit 25 — both are inhibits, not enables), asks for maximum performance (HWP `IA32_HWP_REQUEST` on Skylake+, otherwise `IA32_PERF_CTL`, on AMD `PSTATE_CONTROL = 0`), and measures the **real** clock from the `APERF`/`MPERF` ratio against the base frequency. `kernel_main`'s idle loop re-samples twice a second so the value is always fresh — a single reading can only return the base, the counters need two samples.
- **Every MSR access goes through `msr_try_read`/`msr_try_write`.** A missing MSR raises #GP, and on a stranger's laptop that must not be a dead kernel: the code sets `g_msr_probe`, and `handle_cpu_exception` skips the faulting instruction (`rdmsr`/`wrmsr` are two bytes each) and reports failure. Verified by probing a deliberately invalid MSR at boot — the kernel printed "#GP перехвачен" and carried on.
- Because the fixup needs the real IDT, `cpu_init()` must run after `init_user_mode()`, which is what actually installs `idt64`.
- **`src/kernel/kernel.c` has a second, dead IDT** (`idt[33]` with `isr_stub_*`/`isr_common_stub`): `init_user_mode` overwrites it with `idt64`, whose vectors point at `isr_*` in `src/asm/interrupts.asm`. When touching exception handling, that assembly file is the live path.
- `interrupt_common` in interrupts.asm **used to lose `rbx`**: it pushed 15 registers and popped 14, so a handler that returned would resume with the stack 8 bytes off and `iretq` would take the error code as RIP. Nothing noticed because the handler never returned (BSOD, or the process was killed and the scheduler switched away) — the MSR fixup is the first path that does return.
- Syscall **130 `sys_cpuinfo`** exposes model, cores/threads, base/max/current MHz, turbo and the governor; shown by `fastfetch` and by overSettings → "О системе". The current frequency is measured, not the nominal number from the brand string.
- **CPU time is charged per task**: `timer_isr_handler` adds its tick to whoever was on the CPU (`task_t.cpu_ticks`, and the PIT runs at 1000 Hz, so a tick is a millisecond), `sched_task_list` reports it in `cpu_ms`, and overTask divides the growth by the elapsed time — the same arithmetic as `/proc/stat`. Idle time is the share of **pid 0** (its loop sits in `hlt`), so the overall load is everything except pid 0.
- Syscall **131 `sys_diskinfo`** gives the partition size and the sectors moved to and from the stick since boot (`g_blk_rd_sectors`/`g_blk_wr_sectors` in drivers/blk.c, all disks together). Used space is **cached for ten seconds in the kernel**: `fat32_get_stats` walks the whole FAT, and overTask asks every second — on a real USB stick that polling would have shown up in its own I/O counter.

### Worker cores (`src/kernel/smp.c`, `src/asm/ap_boot.asm`)
- **The kernel stays single-processor; the other cores are compute workers for programs.** Scheduler, drivers, FAT and every lock-free global in the kernel assume one CPU, so the APs never enter that code. A program starts a function on a free core (`ov_worker_start(fn, arg, stack_top)`, syscall 138); it runs in Ring 3 in the program's own address space and may only call `ov_wait_u32` (139), `ov_worker_id` (142) and exit (0/141). Everything else returns -1. Workers must not allocate (no brk), open files or draw — the main thread prepares memory for them.
- Bring-up: the loader's "Starting Worker Cores..." line calls `smp_init(threads)`: the BSP's LAPIC is software-enabled (LINT0 left/made ExtINT, then it checks the PIT still ticks and backs out if not), `ap_boot.asm` is copied to phys `0x8000` with the BSP's CR0/CR4/EFER/PML4 patched in, then broadcast INIT-SIPI-SIPI. Each AP takes an index with `lock xadd`, gets its own stack in `smp_ap_stacks` and its own GDT+TSS (the busy TSS descriptor cannot be loaded twice), loads the shared IDT (`idt_load_this_cpu`), copies the BSP's PAT (WC for the screen) and parks in `hlt`. xAPIC and x2APIC both work; >`SMP_MAX` (16) cores are parked in the trampoline.
- **"Am I on a worker core" is decided by the stack**, not by the LAPIC: `smp_on_ap()` checks RSP against `smp_ap_stacks`. `syscall_isr_stub` does the same compare in assembly and calls `smp_ap_syscall` instead of `syscall_dispatcher`; `default_exception_handler` sends AP faults to `smp_ap_exception`, which marks the fault and returns the core to idle — `smp_poll()` in `kernel_main`'s loop then kills the owning process. A worker crash never BSODs the kernel.
- One IPI vector (`0xF0`) does everything; what to do is in the core's slot: run (state ASSIGNED), stop (`stop`), flush the TLB (`flush_req`/`flush_ack`), or just wake from `hlt` (`SYS_WAKE`). `ap_idle` uses `cli; check; sti; hlt` so a wake between the check and the `hlt` is not lost.
- **Memory safety hooks**: `vmm_destroy_address_space` first calls `smp_stop_space(cr3)` (exit, kill, execve all go through it), `sched_send_signal` stops a killed process's workers at once, and `vmm_unmap_page`/`vmm_unmap_page_take` call `smp_flush_space` so a worker never keeps a stale TLB entry to a freed page. All waits are TSC-bounded and work under `cli` (the BSP is often inside `sched_exit_current`).
- `smp.c` is built with `-mgeneral-regs-only`: the kernel's other C files may use SSE, and a handler on a worker core must not clobber the xmm registers of the program computing there.
- `/programs/smptest.prg` is the regression test: same work on one core and on all (QEMU -smp 4: 86 → 24 ms), 200 wake/sleep rounds, `smptest spin` (exit with spinning workers), `smptest crash` (NULL write on a worker). `-smp 1` boots with "Running on a single core" and everything falls back to the main thread.
- stress.sys still wakes the cores with its own INIT-SIPI; do not run it while a program uses workers.

### Boot (what the loader really does)
- `src/kernel/loader_kernel.c` used to be theatre: a list of `[ OK ]` lines hard-coded to success for things `kernel_main` had already done. It is now a real init: every line is a real check of a real subsystem with real numbers (RAM, CPU, PCI devices, screen mode, the stick's size, the volume's size), the result is kept in `boot_report_t` (`boot_get_report()`), and the parts that belong to it — PCI, display, USB, the root file system, PS/2, audio, Ethernet, kernel modules — are actually brought up there. The timer line is checked by watching `timer_ticks` move.
- **The loader loads kernel modules**: `/etc/modules`, one name per line, `#` for comments, a bare name is looked up in `/utils` (like `modules-load.d`). Before that a `.sys` module could only be loaded by hand from the shell.
- The boot line must not walk the FAT: used space costs hundreds of sector reads from the stick (seconds on real USB), so the loader prints the volume size from the BPB (`fat32_total_mb()`), and the used amount is left to `free`/overTask, which get it from the ten-second kernel cache.
- **The boot log looks and reads like systemd on Arch, and it is in English.** Each step prints a dim `         Starting Foo...` line first and then `[  OK  ] Started Foo: <numbers>.` (or `[FAILED]` in red), so the lines scroll by the way a Linux user expects. English on purpose: it is kernel-level service output, the console font is CP866, and the messages must look the same on any machine. Everything user-facing (OOBE, greeter, desktop, shell) stays Russian.
- **Drivers do not chatter on the boot screen.** `xhci.c` keeps a `s_verbose` flag (default 0, like a low `loglevel`): informational lines are suppressed and only errors are printed, because the result already lands in the `Started USB Host Controllers:` line. `usb-debug` in the kernel shell toggles it, `usb` (alias `lsusb`) prints which controller drives the bus and what sits on the ports. `lspci` (alias `pci`, `cmd_lspci` in pci.c) lists the PCI bus like `lspci -nn`: address, class, `vendor:device`, and the subsystem id for network cards (with Intel Wi-Fi only the subsystem tells the modules apart); there is no `pci.ids` name database, only a short vendor table.
- **`pmm_mark_region_used` did not count**: it set bitmap bits without touching `pmm_used_blocks`, so the kernel's own 36 MB (and anything else reserved that way) was missing from `free`, `fastfetch` and the task manager. It now counts the free→used transition, and the boot line shows "занято 35 МБ" instead of 0.

### USB: layers, controllers and disks
- **Layers, each knowing only the one below** (the user asked for this order after `xhci.c` used to call `ehci_init()` and the block layer `usbblk.c` knew both controllers and the watchdog):
  - `drivers/usb/usb.c` / `usb.h` — the common USB layer: `usb_bootstrap()` (brings up **every** controller present: xHCI first, EHCI whenever it exists, because in Smart Auto the stick may be on EHCI even when xHCI came up), `usb_poll()` (hot plug for all controllers), `usb_lock()` (one bus exchange at a time), standard requests/descriptors and the BOT/SCSI structs.
  - `ehci.c` (controller, control transfers, enumeration of every root port and every hub port, `ehci_poll`) + `ehci-msc.c` (BOT over EHCI, a **table** of sticks with their own address, endpoints and DATA0/1 toggles).
  - `xhci.c` (controller, rings, commands, slots, enumeration, `xhci_poll`) + `xhci-msc.c` (bulk endpoints, BOT/SCSI, read/write) + `xhci-priv.h` (internals shared by those two only; the rest of the kernel sees `xhci.h`).
  - `drivers/blk.c` — the disk registry: a driver that found a stick calls `blk_add(ops, handle, ...)` and gets a disk number; `blk_gone()` when it is unplugged. `blk_read(disk, ...)`/`blk_write` dispatch through the ops. No policy, no mounting.
  - `fs/mount.c` — what to do with disks (see the next section). Nothing below it knows about file systems.
- **Bus access is serialised by `usb_lock`**, taken only at driver entry points (the blk ops and `usb_poll`). The hot-plug poll runs in its own thread while sectors are read from other tasks' syscalls, and both controllers have a single shared exchange path (xHCI's event ring, EHCI's async schedule) — two concurrent exchanges would take each other's answers. Lock order is always `fs_lock` → `usb_lock`; `usb_poll` never touches the file system.
- **`vfs_init()` belongs to the kernel, not to a bus driver.** It used to be called from `ehci.c` after the stick mounted, so on a machine whose BIOS is set to "xHCI only" (where EHCI disappears from the PCI bus entirely) `/dev` was never populated: `/dev/fb0` could not be opened and `desktop.prg` quietly exited with code 1, while the console setup wizard spun forever reading a `/dev/tty` that did not exist. It is called from the loader now, before anything opens a file.
- **`fat32.c` calls `blk_read`/`blk_write` with the disk of the selected volume, never a controller**, which is what lets overOS boot and run entirely off xHCI. Writing on xHCI goes through SCSI `WRITE(10)` over the same BOT path; it was switched on only after reads had booted the system on the user's real laptop, and verified end to end in QEMU (a user created by the console wizard on an xHCI-only machine was on the image afterwards).
- **A new process is created suspended** (`sched_spawn_process` leaves it `TASK_SLEEPING` with no wake condition; `sched_start_process` releases it). Otherwise the child could be scheduled before its parent had set the TTY's foreground pid and graphics mode, and its first `open("/dev/fb0")` or read of `/dev/tty` was refused — a race whose outcome changed with the speed of the storage path.
- `ehci_bulk_transfer` returns immediately when the controller was never initialised. It used to dereference a null `op_regs` and spin in `while (op_regs->usbsts & ...)`, which on a machine without EHCI froze the boot on "Mounting Root File System..." with no message at all.
- `usb_bootstrap()` (usb.c) reports as "the" driver whichever controller has storage (xHCI preferred); `pci_find_usb_by_progif(0x30/0x20/...)` finds them by PCI prog_if. `usb` (alias `lsusb`) in the kernel shell lists the controllers, every disk of the registry and the mounted volumes; `usb-debug` toggles verbose driver output (`usb_set_verbose`).
- `src/drivers/usb/xhci.c` is at stage two. Stage one: PCI probe, BIOS handoff through the USB Legacy Support extended capability (while the firmware owns it, every register access can trap into SMM), controller reset, DCBAA + scratchpad + command ring + event ring with ERST, start, a No-Op command to prove the rings answer, and a port scan with reset and speed detection. Stage two is device enumeration and storage: Enable Slot → input context (slot + EP0 with a transfer ring) → Address Device → `GET_DESCRIPTOR` over EP0 → Configure Endpoint for the two bulk endpoints of a mass-storage interface → USB BOT (CBW / data / CSW) carrying SCSI `INQUIRY`, `TEST UNIT READY`, `REQUEST SENSE`, `READ CAPACITY(10)` and `READ(10)`. A stick found this way is registered in `drivers/blk.c` (`xhci_msc_attach` in xhci-msc.c), and that is where the **root file system is mounted from when there is no EHCI** — verified in QEMU with the image on `qemu-xhci` and no EHCI at all: the system boots to the graphical session.
- **A short bulk transfer is an error, not a success.** `xhci_scsi` requires the exact length: a half-delivered sector looks like ordinary data and breaks something far away instead.
- When `xhci_init()` fails it says why, always, even with `s_verbose` off, and prints BAR0 / CAPLENGTH / HCSPARAMS1 in hex — on someone else's laptop that line is the only evidence there is. Registers reading as all-zero or all-ones, or a controller claiming zero ports, are treated as failure: before that, init "succeeded" with zero ports and the system hung later with no explanation.
- **xHCI's 64-bit registers are written as two 32-bit words**, low half first (`wr64`), the way real drivers do it: this controller already proved picky about access width when a 2-byte read of HCIVERSION came back as zero. The event ring is read through a `volatile` pointer, because the controller writes those TRBs by DMA, and timeouts are counted in kernel timer ticks rather than in empty loops — a port-0x80 delay loop is worth a different number of microseconds on every machine, so "100 ms" could really be two.
- The PCI command register also gets **INTx disabled** (bit 10): there is no interrupt handler for the controller, events are polled, and an unserviced legacy line on real hardware wedges the machine.
- **Ports are not readable the instant the controller starts.** After a real HCRST the port state machines need power, debounce and (on USB 3) link training, so `xhci_scan_ports` powers every port first, waits ~120 ms, and then polls in up to five passes of 200 ms, stopping as soon as a storage device answers. Reading PORTSC immediately after start reported "13 ports, 0 connected" on a laptop that had three devices attached — and, before the controller was really being started at all, the same read returned the firmware's stale state and looked right.
- **Writing PORTSC back must use `portsc_neutral()`.** PED (bit 1) is write-1-to-**disable**, and PR/LWS/WPR and the change bits all *do* something when written as 1. The old mask only removed the change bits, so "clear the connect-change flag" on a USB 3 port that had already enabled itself turned that port off again — the stick showed as connected and then could not be talked to.
- **One line per connected port** (`report_port`): speed, VID:PID and "storage N MiB" / "not storage", or the exact step and completion code where enumeration stopped (`FAIL(step, code)` in `xhci_setup_device`). It goes through `dbg()` — `kdebug` in a `DEBUG_MODE` build, or always after `usb-debug` — because once xHCI worked on the user's laptop the lines were just noise on the boot screen.
- **The device needs `SET_CONFIGURATION` too.** Configure Endpoint only tells the *controller* about the bulk endpoints; the stick itself stays in the Addressed state until it gets the standard request, and its bulk endpoints do not exist yet. QEMU's usb-storage answered anyway, a real stick did not ("storage did not answer SCSI" on the user's laptop). `xhci_control_nodata` sends it with `bConfigurationValue` from the configuration descriptor.
- **Wait for *your* transfer event**, matched by slot, endpoint (DCI) and TRB address (`xhci_wait_transfer`). Taking the first transfer event that arrives lets one stray event (a short packet, say) shift every later answer by one. Data TRBs carry ISP so a short packet is reported where it happened.
- **A STALL halts the endpoint until it is cleared**: Reset Endpoint → Set TR Dequeue Pointer (to the current enqueue position and cycle) → `CLEAR_FEATURE(ENDPOINT_HALT)` to the device (`xhci_clear_halt`). Without it every later transfer waited a full second for nothing. BOT also reads the CSW after a stalled data stage, as the spec requires, and the probe gives up on a dead transport instead of retrying TEST UNIT READY ten times — that is what made the laptop look frozen on "Starting USB Host Controllers...".
- In Smart Auto mode the BIOS routes the ports to EHCI and every xHCI PORTSC reads `0x2A0` (powered, RxDetect, nothing attached). That is normal, so the PORTSC dump is printed only when there is no EHCI on the bus (or with `usb-debug`).
- **A Low/Full-speed device's EP0 packet size is unknown up front** (8/16/32/64). The slot starts with 8; a device with 64 then sends a bigger packet and the controller reports **Babble (cc 3)** — that was the laptop's Full-speed port 7. So for LS/FS only the first 8 bytes of the device descriptor are read, byte 7 gives the real size, and an Evaluate Context command updates EP0 before the full read. This matters beyond that one device: USB keyboards and mice are almost always LS/FS. QEMU attaches its usb-kbd/usb-mouse to xHCI as High-speed, so this path is only testable on real hardware.
- **CAPLENGTH is not small.** The sanity check used to reject anything above 0x40, which threw away a perfectly healthy Intel controller on the user's laptop (BAR0 `0xF7A00000`, first dword `0x01000080`: CAPLENGTH 0x80, version 1.0). The spec allows up to 0xFF; only a value below 0x20 is nonsense.
- Endpoint numbering in xHCI is by **DCI** = `ep_num * 2 + direction` (EP0 is 1), and that same number is both the index of the endpoint context inside the device context and the value written to the slot's doorbell. The input control context's add-flags bit is the DCI too, and the slot context's "context entries" field must name the **highest** DCI in use, or Configure Endpoint is refused.
- A `Configure Endpoint` input context must carry the slot context **copied from the output (device) context** the controller filled in during Address Device; building a fresh one from scratch loses the address and the controller rejects it.
- xHCI talks in **rings of TRBs**, not registers: a command goes into the command ring, a doorbell write tells the controller, and the answer arrives as an event in the event ring with a cycle bit that flips each lap. Rings are PMM pages (contiguous, below 4 GB — the controller needs a physical address); the CPU reaches them through the direct map.

### USB keyboards and mice (`drivers/usb/hid.c`, `xhci-hid.c`)
- **HID boot protocol on xHCI.** `parse_config` records interfaces of class 3, subclass 1, protocol 1 (keyboard) / 2 (mouse) and their interrupt IN endpoint; `xhci_hid_attach` configures those endpoints (type 7, interval converted to 2^n·125 µs: bInterval is milliseconds at LS/FS, an exponent at HS/SS), sends SET_CONFIGURATION, SET_PROTOCOL(boot), SET_IDLE(0) and keeps `XHID_QUEUED` Normal TRBs queued per endpoint.
- **Those TRBs target interrupter 1**, a second event ring set up in `xhci_setup_rings` and drained from the timer ISR (`usb_hid_tick` → `xhci_hid_service`, every 1 ms), which re-queues a TRB for every report. They cannot go to ring 0: `xhci_wait_transfer` and friends skip and **discard** events that are not theirs, so a mouse report there would vanish (or be eaten in the middle of a sector read). Removal goes through `xhci_hid_detach` (with interrupts off) before `dev_release` frees the rings.
- `hid.c` is controller-independent: keyboard reports are diffed against the previous one into **PS/2 set-1 scancodes** (E0 prefixes included, modifiers from the bitmap, typematic repeat 500/33 ms since USB has none), mouse reports into screen-space deltas. Both go into a lock-free ring and are consumed in `ps2_hw_service` → `usb_hid_drain` → `kbd_scancode` (the per-scancode body of the old PS/2 loop) / `mouse_feed_report` (the second half of the old PS/2 packet code). So TTYs, Ctrl+C, the compositor, `ui_raw_keys` and the games' raw mouse see one keyboard and one mouse, whatever is plugged in.
- **Intel port routing**: on Intel PCHs in BIOS "Smart Auto", every external socket starts on EHCI (behind its RMH hub) and xHCI sees empty ports. `xhci_route_intel_ports` writes XUSB2PR/USB3_PSSEN from their masks (0xD0..0xDC in the xHCI's PCI config), as Linux's `usb_enable_intel_xhci_ports` does, before the port scan — so the boot stick moves to xHCI too. `USB_ROUTE_TO_XHCI` in `kernel/config.h` turns it off. HID on EHCI (split transactions through the RMH's TT, a periodic schedule) is not written yet.
- **No PS/2 controller is a valid machine**: the ports then read 0xFF, which means "data available", and both the drain loop in `init_ps2_mouse` and `ps2_hw_service` spun forever — boot hung on "Starting PS/2 Keyboard and Mouse...". `g_ps2_present` is set from `inb(0x64) == 0xFF`; the loops are bounded.
- Tested in QEMU with `-machine pc,i8042=off -device qemu-xhci -device usb-kbd -device usb-mouse` (login, terminal, Shift, arrows, hot add/remove of a second keyboard); `lsusb` prints the keyboard/mouse counts. QEMU's `sendkey` goes to the most recently added keyboard.

### Several sticks, `/media` and hot plug (`fs/mount.c`, thread `storaged`)
- **`fat32.c` has a volume table** (`FAT32_MAX_VOLS`, volume 0 is the root). All former globals (`g_bpb32`, `g_fat_lba`, `g_current_cluster32`, the FAT sector cache...) are macros on the fields of the *selected* volume (`fat32_select`), so the driver code itself did not change. `fs.c` selects the volume before every call, under `fs_lock`.
- **Routing in `fs.c`:** a path inside `/media/<name>` (absolute, or relative while the caller's cwd is there) is normalised (`fs_abs`: cwd + name, `.`/`..`), `mount_route` picks the volume and the driver gets the path *inside* the volume. Everything else goes to volume 0 exactly as before, relative names and all, so old code keeps its habits. `/media` itself is a real directory in the image (`mmd ::media`) and its listing gets the mounted volumes appended (`mount_media_entries`). Mount names match **case-insensitively**: `perm_normalize` lowercases every path (so `chdir` passes `/media/teststick` for `TESTSTICK`); a case-sensitive compare made `cd` fail while `ls` worked.
- **The root** is chosen at boot by `mount_root()` (`fs_mount(0)`): the oldest disk with a FAT32 partition containing `/sys/KERNEL.BIN`; with none, the first FAT32 found (test images). Its identity is kept: VID:PID, block count, partition LBA and the volume serial from the BPB.
- **`storaged`** (created by `mount_start()` in `kernel_main`, after `sched_init`) wakes every 500 ms: `usb_poll()`, then walks the disk registry. A new disk: if the root is lost and this is the same stick (`is_root_again`: identity + serial on the old LBA) the root is remounted; otherwise its partitions are scanned (`part_scan`: MBR, GPT, or a whole-disk "superfloppy" FAT; type `0x7F` is our stage2 area) and every FAT32 is mounted as `/media/<label>` (label from the root-dir volume entry first, then the BPB; none or "NO NAME" → serial `ABCD-1234`; clashes get `_2`). exFAT/NTFS/FAT16 are recognised by their boot sector and reported as unsupported. A gone disk: its volumes are unmounted and the registry slot released (`blk_release` — only after that, so a new stick cannot reuse the number while a volume still points at it).
- **Hot plug detection.** xHCI: `xhci_poll` treats a bound port without CCS or without PED as gone (**not** CSC alone — some controllers raise it during USB 3 link training, and the root would start "disappearing" twice a second) and brings up unbound connected ports; a port where enumeration failed is marked and left alone until it is unplugged, otherwise every poll cost a slot and 100 ms. `xhci_dev_gone` disables the slot and now returns its DMA pages (the old code leaked ~5 pages per unplug and one page per enumeration). EHCI: root ports by their CSC bit; hub ports (Intel's RMH — every external socket on those laptops is a port of it) by `GET_STATUS` every second, with `C_PORT_CONNECTION` cleared on every attach so it only reports real changes. A stick that stopped answering while its port still looks connected (always the case behind the RMH) is removed and its port re-enumerated every 2 s — that is what used to be "bring all of EHCI up again" in the old watchdog.
- **Unplugging the system stick** used to freeze the machine; now every disk operation on a gone device fails immediately (xHCI checks CCS before each command, EHCI marks the stick gone on a non-STALL transfer error, a 5 s timeout or an empty root port), volume 0 is detached (`fat32_detach_disk`: no read reaches the bus, but paths still answer "no"), and the critical notification "Флешка с системой отключена" stays until the same stick is back. Writes in flight at that moment are lost, and a half-updated FAT stays half-updated — the "снова на месте" notification says to check what was being saved.
- **Removable volumes are world-writable** (`perm_is_removable` in users.c: everything under `/media/<name>` is 0777, `/media` itself 0755), as Linux mounts vfat with the session user's uid; such paths are never written to the root stick's `/etc/perms`.
- **FSInfo**: the first FAT change on a mount sets the free-cluster hint to `0xFFFFFFFF` ("unknown", allowed by the spec). The driver never maintained it, which was harmless on our own stick but not on a stranger's that Windows will trust afterwards; fsck now says "uninitialized" instead of "wrong".
- Syscalls: **132** `sys_storage_state` (0 ok, 1 root lost; 2 "foreign" no longer happens — another stick is simply mounted in `/media`), **134** `sys_mounts` (`ov_mount_t`: name, label, device name, path, size, flags), **135** `sys_eject(name)` (unmounts every volume of that disk; allowed to any user, like the session's udisks), **136** `sys_proc_exe(pid)`.
- Verified in QEMU, EHCI and xHCI: two sticks at boot, hot-plugging a second stick in a session, `cat`/`echo >`/`cd` on it (the file is on the image, fsck clean), pulling it out, then pulling the root out and back with a file written afterwards persisting.

### Notifications (`kernel/notify.c`, `Desktop/notifier.c`, `common/ovnotify.h`)
- **System notifications** are queued by the kernel (`knotify_post`, 16 entries, oldest dropped) and fetched by the compositor four times a second (**133** `sys_notify_poll`, root only). `mount.c` posts "Обнаружено устройство USB" with the actions `open:/media/X` and `eject:X`, "Устройство можно извлечь" (replacing the first card, same id), "Устройство отключено" when pulled without ejecting, and the root's critical card with the fixed id `NOTE_ROOT`, replaced by "снова на месте" when it returns. Bodies are 200 bytes: Cyrillic is two bytes per letter and 136 cut every sentence.
- **Application notifications** are a protocol message, not a syscall: `ov_notify(id, title, body, icon)` / `ov_notify_ex` send `WP_NOTIFY` to the compositor; no window is needed (console `notify` = `/programs/notify.prg`, and the shell now finds `/programs/<name>.prg` by bare name, like PATH). The id is chosen by the program and the same id replaces the card, so there is no reply message that a libui program would have to fish out of its mailbox. Buttons come back as `WP_EV_NOTIFY_ACTION` (`ui_notify_action`). **The header (icon and name) comes from the sender's executable**, looked up by pid (`ov_proc_exe` → `appinfo`), never from the message, so a program cannot pose as the system or another app.
- The popups (`notifier.c`) are drawn with `gfx_round_rect_aa` (edge coverage in 1/256 px) and a ring shadow `gfx_shadow_round`: the old `gfx_darken` shadow was a rectangle, and its dark square corners showed through the rounded card. The time line is redrawn whenever its width changes by a pixel, not by 1/40 (that stepped ~9 px every 150 ms). They are Plasma-like cards above the panel, newest at the bottom: a 20 px app icon + name and a close button, a 2 px line showing the remaining time, a 16 px title drawn once (a second pass shifted by a pixel used to fake bold and smeared it), body wrapped by words (4 lines, then "..."), a 48 px icon on the right, action buttons right-aligned. The mouse over a card stops its clock; a click on the card runs the first action; critical cards (orange) never time out and ignore body clicks. **Time only runs while the desktop is on screen** (`dt` is clamped to 100 ms per tick): the loop does not reach `notifier_tick` while a TTY is shown, and the first frame back used to expire a notification that had arrived meanwhile.
- "Открыть" hands the path to a running overFiles (`wserver_hand_over` → `WP_EV_OPEN`, overFiles now reads `ui_open_request`) or starts it with the path. overFiles shows "Устройства" in its sidebar (from `ov_mounts`) with an eject button, and leaves a stick's directory by itself when the stick goes away.

### Program resources: icon, name and class inside the `.prg`
- The DPRG header's last field (formerly `reserved`, now `res_offset`) points to a `DRES` directory appended after the code: entries `{type[4], offset, size}` for `ICON` (SVG text), `NAME` (UTF-8 display name) and `APPI` (application class). `tools/elf2prg.py --icon --name --app` writes it; `app.mk` passes `icon.svg` from the app directory and `APP_NAME`/`APP_ID` from its makefile. The kernel loader ignores everything after `code_size`.
- `common/prgres.h` (`prg_resource`) reads them; the compositor caches per path in `appinfo.c` (the dock is rebuilt every frame and must not open files each time), and its icon cache takes a path starting with `/` as "the ICON resource of this program". Window title icons use `window_t.exe` (filled from `sys_proc_exe` on `WP_CREATE`), the dock uses the pin path or the window's exe, the start menu uses `NAME`. The four hard-coded tables (`window_svg_of`, `dock_svg_of`, `dock_icon_of`, `app_label_of`) and the copies of app icons in `icons.h` are gone.
- `task_t.exe` (96 bytes, before `fpu_state`) is set by the program loader and `execve`, copied on `fork`; a relative path is resolved against the caller's cwd.
- libui gained `ui_icon(w, x, y, size, name, tint)` (system icon or `.prg` path, rasterised once per process into a 24K-pixel arena) — overFiles uses it to draw a program's own icon on its file, like Explorer does with `.exe`.
- `src/files/icons/` now holds only theme icons (sound, network, brightness, launcher, `drive-removable`, `dialog-warning`, `dialog-information`, `media-eject`, `notifications`); application icons live in `src/files/progs/<App>/icon.svg`.

### Kernel core
- Boot: `src/boot` stage1 MBR → stage2 (E820 memory map, unreal mode, FAT32 reader loads `/sys/KERNEL.BIN` to 1 MiB, 16-bit C VBE mode menu) → `entry_kernel.asm` (long mode, paging) → `kernel_main`.
- `src/kernel/user_mode.c` is the syscall dispatcher (one big `switch`). Read it first when touching the user/kernel boundary. Numbers 40–48 are retired: the window server moved out of the kernel into the compositor.
- `sched.c`: preemptive round-robin on the PIT, per-task 64 KiB kernel stack, `TSS.RSP0` updated on switch, `switch.asm` does context switches. `fork`/`execve`/`waitpid`/`kill` are syscalls 30–33.
- **`switch_to` saves FPU/SSE state** with `fxsave`/`fxrstor` into `task_t.fpu_state` (512 bytes, 16-aligned; the struct is page-allocated so the field really is aligned). `switch.asm` reads the area through `task_t.fpu` at **offset 16**, pinned by a compile-time check on `offsetof` in sched.h — do not insert fields before it. A new task gets a clean state (FCW `0x037F`, MXCSR `0x1F80`); `fork` gives the child a snapshot of the parent's live state. Without this, any two tasks using SSE clobbered each other: `src/programs/fputest.prg` is the regression test (two forked processes hold patterns in xmm0–xmm7 across sleeps; it reported 299/300 rounds corrupted before the fix and 0 after).
- **A process is named after the file, not the path**: `prog_spawn` strips the directories before `sched_spawn_process`, because `task_t.name` is 16 bytes and "/desprogs/ovfiles.prg" used to show up in `ps` as "/desprogs/ovfil".
- `prog_loader.c` loads DPRG into a fresh PML4 (`vmm_create_address_space`). Binaries with `PRG_FLAG_DESKTOP` are refused from the TTY shell. `desktop.prg` itself is special-cased by filename (gfx mode, launched from `/autostart`, PID 2 protected from `kill`, can't be exec'd twice).
- FAT32 driver note: lookups validate the LFN checksum against the 8.3 entry, and `fat32_remove_file` also deletes the LFN entries. Otherwise an orphaned long name gets attached to a new file in the reused slot.
- **Long names are UTF-8 at the API and UTF-16 on disk.** Reading collects the UTF-16 code units by position first (`g_lfn_u16`) and converts the whole name once it is complete, because a character and a byte are not the same length; writing converts UTF-8 → UTF-16 and counts LFN entries in **code units**, not bytes. Non-ASCII bytes used to be replaced with `_` in both directions, so Russian file names were unusable. The 8.3 alias replaces anything outside the allowed set with `_` — the real name lives in the LFN entries.
- **Caps Lock** is tracked in `ps2_hw_service` (scancode `0x3A`), which also drives the keyboard LED (`0xED` + mask; the controller's `0xFA`/`0xFE` answers are dropped there). It flips the case of **letters only** — both consumers go through `caps_shift()`, because XOR-ing it into Shift would turn `1` into `!`. The compositor keeps its own copy in `g_caps_on` (window.c, toggled in `window_post_key`), `km_translate` takes it as a parameter, the taskbar draws a padlock left of the tray (and shortens the window list by its width, as in KDE), and the greeter warns "Caps Lock включен" next to the password field — the font has no `ё`, so don't put one in a greeter string.
- **Switching TTY steals the modifier release**: Alt goes down in one TTY and the `0xB8` lands in the next one, so the compositor kept Alt pressed after Alt+F2 → Alt+F1 and silently stopped sending typed text to windows (keys still arrived, only `k.text` was empty). `tty_switch` now calls `kbd_clear_modifiers()` and pushes Shift/Ctrl/Alt release codes into the target TTY.
- **The TTY has one layout — US**, as in a Linux console: `kbd_layout`, the CP866 table and the Alt toggle are gone from keyboard.c (and with them the `rus`/`англ` service commands). Russian is typed in the graphical session, where the compositor applies the layout (`src/libs/common/keymap.h`). File names and paths are still UTF-8 everywhere, and the console converts UTF-8 back to CP866 when drawing (`utf8_to_cp866` in kernel.c), so a Russian file name from the GUI prints correctly in `ls`.
- Storage: EHCI / xHCI + USB MSC/BOT (`drivers/usb`) → disk registry (`drivers/blk.c`) → volumes and `/media` (`fs/mount.c`) → FAT32 → `vfs.c`/`fs.c` (global `fs_lock` spinlock). FAT16 is gone; `fat_dir_entry_t` now lives in `fat32.h`. Other drivers: PCI, ACPI, PS/2 kbd/mouse, ethernet, Intel HDA (`hda.c`, syscall 70 sub-commands for PCM output).
- The console belongs to the TTY, not the system: cursor, scrollback, input line and cwd are fields of `tty_t`, and `tty_console()` returns the TTY of the *calling task* (active TTY for kernel threads without one). A shell in a background TTY writes into its own buffer; `flush_buffer` only touches the LFB for the active TTY. Each TTY gets its own scrollback ring, indexed with stride `screen_width` — the same stride `tty_spawn` allocates (a mismatch here overwrote kernel memory and killed the box on the first scroll).
- The FAT driver's directory position is per operation, not system state: `fs.c` enters `fs_caller_cwd()` (the process's `task_t.cwd`, or the TTY shell's path) before each call and caches where the driver stands. `fs_touch`/`fs_make_folder` take full paths (`fs_create_entry` walks to the parent itself).
- Multi-TTY: tty1..tty6 via Alt+F1..F6 (`MAX_TTYS`). TTY 2..6 are allocated lazily in `tty_spawn`. The kernel shell supports Shift (US and CP866 Russian). Kernel-wide flags (`FUN_EDITION`, `DEBUG_MODE`, `BSOD_ENABLED`, version) live in `src/kernel/config.h`.
- **The console decodes any UTF-8**, not just Cyrillic: `utf8_feed` collects the code point byte by byte and `uni_to_cp866` maps it. CP866 has no typographic punctuation, so an em dash, quotes, an ellipsis and a middle dot are replaced with the nearest ASCII; before that only the two-byte `D0`/`D1` prefixes were understood and "—" printed as the raw bytes "тАФ".
- **Two console palettes, as in Linux**: `tty1..tty6` keep the classic look (black background, bright VGA colours, `CONT_*` in contheme.h) and the pseudo-terminal in the overTerm window gets the soft One Dark theme (`CON_*`). Everyone writes with the `CON_*` names; `con_tint()` in kernel.c translates them to the classic set at the lowest level (`draw_char_ex`, `fill_rect`, `clear_screen`, `draw_cursor`) whenever the console is not a pty, so no caller needs to know where it is printing.
- **One palette for the whole console**: `src/libs/common/contheme.h` (`CON_BG`, `CON_FG`, `CON_GREEN`…), included by the kernel, by `/sys/sh.prg` and by anything else that writes there — the kernel's `CFLAGS` carry `-I src/libs/common` for it. The background is a Breeze-like dark grey instead of pure black and the ANSI colours are muted; before that the colours were hex literals scattered across files and the console looked like debug output.
- **Command history lives in the TTY driver**, not in the shell: the kernel assembles the line (canonical mode), so only the kernel can act on the arrow keys. `tty_t` keeps a ring of 24 commands (`tty_hist_add/count/get/number`), Up/Down in `tty_line_read` redraw the line, and syscall **129 `sys_tty_history`** lets `history` in the shell print the list. A real Linux console has no history because bash puts the terminal in raw mode and does it itself; we have no raw mode, so it belongs here — and that is why it works in the graphical terminal for free. The shell turns recording on with `ioctl(0, OV_TTY_HIST, 1)` and off before exiting; otherwise the user name typed at `login.prg`'s prompt would be recorded as a command. Passwords are never recorded (`echo_off`).
- Backspace wraps to the previous row when `cursor_x == 0`, because a recalled long command spans several rows and could not be erased otherwise.
- **A console has its own geometry, not the screen's**: `tty_t.w_px`/`h_px`. Every console primitive (`put_pixel`, `fill_rect`, `clear_screen`, `scroll_screen`, `draw_char_ex`, the line wrap in `kputc`, the `fastfetch` layout) indexes by them. For tty1..tty6 they equal the screen; for a pseudo-terminal they are the size of a window. Anything still reading the global `screen_height` here silently draws past the bottom of a pty and the output disappears — that was the first `fastfetch` bug in overTerm.

### Pseudo-terminals (`/dev/pts` equivalent)
- `TTY_SLOTS = MAX_TTYS + MAX_PTYS` (6 + 4). Slots 6..9 are pseudo-terminals: an ordinary TTY of the system — same console, same keyboard queue, same `/sys/sh.prg` with every command including `fastfetch` — whose picture is never blitted to the LFB. The graphical terminal reads it and draws it itself. There are no pipes in the kernel and a GUI terminal does not need them for this.
- `pty_open(w_px, h_px, uid, gid, owner_pid)` allocates the buffers, starts `pty_shell_loop` (a kernel thread that runs `/sys/sh.prg` with the caller's credentials, no login prompt — like xterm) and puts the user's home directory in `current_path`. Syscalls: **123 pty_open, 124 pty_read (a copy of the pixels), 125 pty_key (a scancode into its queue), 126 pty_close, 127 pty_alive**; only the owning process may touch its own pty.
- Three places had to learn that pty ids are `>= MAX_TTYS`, and each one broke it differently: `tty_console()` fell through to the **active** TTY, so the shell printed over the real screen; `tty_is_foreground()` returned 0, so the first read of `/dev/tty` was refused and the shell looped printing prompts; the "background TTY does not draw" guard in `syscall_dispatcher` swallowed its output. A pty is never active, so it must be exempt from that guard.
- `task_create_kernel` links the task into the scheduler ring **before** the caller can set `tty_id`, so `pty_open` does it with interrupts off — otherwise the first lines of the shell land in whatever TTY is on screen.
- Buffers are freed by the shell thread itself (`pty_free_buffers`) after `pty_close` marks the slot dead: it is the only thing that can still write into that console.

### Shell and login in Ring 3
- `tty_shell_loop` is only a getty now: it prints the TTY banner and runs `/sys/login.prg`, restarting it if it dies. The in-kernel shell (`main.c`) stays as the fallback when that program is missing, and its service commands are reachable from userspace through `sys_kcmd` (118).
- `/sys/login.prg` (`src/programs/login.c`) runs as root: first-run setup (console OOBE — language, time zone, second layout, admin user), then login prompt, `sys_auth`, and `sys_spawn` of the shell **with the user's uid/gid** (login itself stays root, as getty does).
- `/sys/sh.prg` (`src/programs/sh.c`) is the shell: file commands, `echo text > file`, session commands (whoami, id, su, sudo, passwd, useradd, chmod, chown, stat), `ps`, and running `.prg` programs. `su` changes credentials **in a forked child** — a process cannot raise itself back, so a shell that called `sys_su` on itself would stay the other user forever.
- TTY input is canonical in the kernel (`tty_line_read` in keyboard.c): echo, Backspace, layout and Shift live in the driver, and a program just reads a line from `/dev/tty`. `ioctl(0, OV_TTY_ECHO, 0)` turns echo off for passwords.
- Only the foreground process of a TTY may read it. The shell hands the keyboard to a child with `sys_tty_setfg` (112, like `tcsetpgrp`) and takes it back afterwards; taking it back is allowed when the previous owner has died, and it repaints the console so a game's last frame doesn't stay on screen.
- New syscalls for this: 112 tty_setfg, 113 ps, 114 chdir, 115 getcwd, 116 su, 117 load_module, 118 kcmd (the bridge to the kernel's remaining service commands), 119–121 lib_open/lib_sym/lib_close (`.ll`).

### Users and permissions (UNIX DAC)
- `task_t` has `uid`/`gid`, inherited on spawn and fork. Kernel threads are root.
- `src/kernel/users.c` loads `/etc/passwd`, `/etc/group`, `/etc/shadow` and `/etc/perms` in `tty1_task_entry`, before autostart. Password hashes are `$ov$salt$sha256(salt+pass)` (`sha256.c`).
- Each `/etc` file is written together with a `<file>-` backup and is read from the backup if the original is missing. Without `/etc/passwd`, root is locked and OOBE runs.
- FAT32 can't store owners, so `/etc/perms` maps `path uid gid octal-mode`. A path without its own line inherits the nearest ancestor's line. Paths are normalized to absolute lowercase (`perm_normalize`), relative to `current_path`.
- `perm_check` also requires X on every parent directory, and root bypasses it. Changes made through `perm_set` / `perm_on_create` / `perm_on_remove` are written back to `/etc/perms`. Call these without holding `fs_lock`, since they take it themselves.
- Checks live in `vfs_sys_open`, syscalls 16/17/18/31/33, `prog_load_module` (X) and the shell built-ins (`login_may*`). Raw keyboard/mouse (6/7/23/24) and `/dev/fb0` are limited to the foreground process of a TTY (`tty_is_foreground`), so a leftover background process cannot read the next user's password. `sys_load_module` (`.sys`) is root-only.
- User syscalls are 80–89: getuid, getgid, setuid, setgid, auth, getpwuid, chmod, chown, stat_perm, passwd.
- `syscall_dispatcher` validates Ring 3 pointer arguments in `user_args_ok`. It walks the caller's page tables (`vmm_user_range_ok` / `vmm_user_str_ok`): every page must be present with USER at every level. Every new pointer-taking syscall must be added there with the **exact** buffer size, because an oversized check rejects valid buffers at the end of mapped memory.
- Orphans go to init: `reparent_children` hands the children of a dying task to `kernel_main` (pid 0), and its loop calls `sched_reap_orphans()` twice a second. Before that a child whose parent died first stayed a zombie forever and its `parent` pointer dangled into a freed page.
- **A dying process frees its address space itself** (`sched_release_space`, called at the end of `sched_exit_current` after switching CR3 to the kernel's PML4 — you cannot tear down the space you are running on; the task's kernel stack lives in the direct map, so it survives the switch). Only the kernel stack is left to the reaper. Waiting for the collector was not enough in practice: a player holding 80 MB (its address space plus ffmpeg.ll) stayed in `ps` with all of it until something eventually reaped it, and the reaper's loop used to **break** on the first zombie it could not release, so everything behind it waited too. It now walks a snapshot of all zombies.
- **A kernel thread must be created with the kernel's PML4**, not with whatever CR3 happens to be loaded (`task_create_kernel`). `pty_open` is called from overTerm's syscall, so the shell thread used to live in that program's address space for good — and when the program exited, its page tables were freed under a running thread.
- **A zombie's memory is released without waiting for the parent** (`sched_release_mm`, called from `sched_reap_orphans` for every zombie): address space, file descriptors and kernel stack go immediately, the task struct stays until somebody waits for the exit code. Linux does the same in `exit()`. Here it matters because the compositor starts applications with `sys_spawn` and never calls `wait`, so every closed window used to leave its whole address space behind — 30 to 50 MB a piece, which is exactly what `ps` showed as dead processes eating memory.
- **A kernel thread that returns becomes a zombie, not `TASK_DEAD`** (`task_exit_stub`): a dead task used to sit in the scheduler ring forever with its page and its 64 KB stack. The reaper frees `KERNEL_STACK_SIZE` for a thread and `PROC_KSTACK_SIZE` for a process.
- `sys_brk` also shrinks: lowering the break unmaps the pages (`vmm_unmap_page_take`) and returns them to the PMM. `src/programs/heaptest.prg` cycles 400 × 4 MB through a 1 GB machine as the regression test; `src/programs/orphan.prg` is the orphan test (run it, then `ps`).
- Ctrl+C goes to the foreground process of the active TTY, except while that process is blitting frames (a game gets Ctrl and C as keys). **Ctrl+Alt+C** always kills it, like Ctrl+Alt+Backspace in X; the compositor (`g_desktop_pid`) is exempt and has its own "выйти из сеанса".
- A fault in Ring 3 kills the process. A fault in Ring 0 is a BSOD, decided by CS in the exception frame and not by `g_user_mode_active`, since the kernel may hold `fs_lock` mid-syscall.
- Program images go through `prg_parse_image` / `prg_map_image` (prog_loader.c), used by both the shell and `execve`. The DPRG header is untrusted. `load_vaddr` must be at least 4 GB (below that is the kernel-only identity map in every process) and below the stack, and the entry point must lie inside the code.
- `kernel_create_fs_entry` walks a nested path component by component, because `fs_change_dir` only understands one level (creating `/home/kris/x` used to fail silently).
- Syscall **19 `lseek(fd, off, whence)`** moves the descriptor's position (`SEEK_SET`/`CUR`/`END`); `ov_lseek`/`ov_fsize` in `ovos.h`. Added for FFmpeg's AVIO, which has to jump to `moov` at the end of an MP4.
- VFS files: `read` honors the fd offset (`fat32_read_at`, partial sectors through a bounce buffer). A `write` at offset 0 replaces the whole file, because existing apps open, write once and close without `O_TRUNC`. Writes at a later offset do read-modify-write up to 16 MB.
- TTY login (`src/kernel/login.c`): the state lives in `tty_t.login_stage`. Before login, and during password prompts, `execute_command` hands the whole line to `login_handle_line`, and keyboard echo is off. Session commands are whoami, id, su, exit, logout, passwd, useradd, chmod, chown and stat. login.c always works on the active TTY.
- Admin model as on desktop Linux: members of `wheel` (`/etc/group` member list) elevate with their **own** password. In the TTY this is `sudo <cmd>` / `sudo -i` (`LOGIN_STAGE_SUDO_PASS`; the command runs through `run_pending_sudo` in main.c, and creds are restored in `login_after_command`). Syscall 93 `sys_sudo(pass)` makes the calling process root; overFiles uses it for its "Access denied → Unlock" dialog. **In admin mode overFiles launches programs with its own (root) credentials** — `ov_spawn(..., -1)` inherits the caller's uid/gid — like "Open as root" in Dolphin; it also stops handing the file to an already running instance, since that process still runs as the user and would only report "Нет доступа к файлу". Outside admin mode nothing changes: the spawned app inherits the plain user.
- The taskbar clock reads the system zone: `settings_load` takes it from `/etc/timezone` (syscall 95) and the clock popup lists every zone from syscall 97 with a draggable scrollbar; picking one writes `/etc/timezone` through syscall 96, like `timedatectl`. `desktop.json` no longer stores a timezone.
- The wallpaper is decoded with the shared `bmp.h`/`png.h` (the compositor's own 200-line BMP parser is gone), so `"wallpaper"` in `desktop.json` can point at a PNG as well; the image is decoded into an ARGB buffer sized from its header and scaled to the screen.
- Desktop settings are per user: after login `settings_set_user(uid, gid)` switches to `~/.config/desktop.json` (created and chowned by the compositor, which runs as root) and the greeter falls back to `/configs/desktop.json`. Brightness, volume and wallpaper are re-applied on every login and logout (`apply_session_settings` in desktop.c).
- System settings live in `/etc/locale.conf` (`LANG`), `/etc/timezone` (tzdata name, offsets in the `g_timezones` table in users.c) and `/etc/vconsole.conf` (`XKBLAYOUT=us` or `us,ru`, which gates Alt layout switching in TTY and Desktop). Syscalls: 95 get, 96 set (root), 97 tz list, 98 lock user.
- OOBE runs when `users_needs_oobe()` is true: `/etc/oobe` is not `1` and there is no user with uid ≥ 1000. Desktop then runs `oobe_run()` (in `greeter.c`) before the greeter. A TTY shows a text wizard instead of `login:` (`LOGIN_STAGE_OOBE_*`). Steps in both: language, time zone, second layout, admin user. Root gets locked. Syscalls: 90 useradd (root), 91 oobe_state, 92 oobe_finish (root).
- The greeter lists users like KDE Plasma: avatars from `/etc/passwd` (uid >= 1000), arrows or a click pick one, only the password is typed, and "Другой пользователь" switches to typing a name. The list refreshes every ~2 s, so an account created in a TTY shows up without logging out.
- Desktop runs as root, like a display manager. `greeter.c` authenticates with `sys_auth` and launches apps with `sys_spawn` under the session's uid/gid. "Выйти из сеанса" kills the session's clients and shows the greeter again.

### IPC and shared memory (kernel)
- `src/kernel/ipc.c`: a mailbox per process (`ipc_msg_t`, up to 256 bytes), service names, and shared memory. The kernel stamps each message with the sender's pid and uid, so they cannot be forged.
- Syscalls 100–111: ipc_send, ipc_recv (blocks in the scheduler, so idle apps burn no CPU), ipc_register (root only), ipc_lookup, shm_create/map/unmap/grant/destroy/size, spawn, getpid.
- Shared pages are tagged `VMM_FLAG_SHARED`: `vmm_destroy_address_space` does not free them and `fork` does not copy them. They are released by `ipc_task_exit` once the last mapping goes away. Shared segments live at `SHM_BASE` (0x5000_0000_0000), one 64 MB slot per id, so the same object has the same address in every process.
- `sched_sleep_ms` and `ipc_recv` put the task in `TASK_SLEEPING` with `wake_tick` / `WAIT_IPC`; the scheduler wakes it. The idle loop uses `hlt`.
- Syscall 109 `sys_spawn(path, arg, uidgid)` starts a program without `fork`, so the compositor no longer copies its own multi-megabyte buffers just to `execve`. Only root may pass a uid/gid other than its own. The launch argument lives in `task_t.arg` (`sys_get_arg`), not in one global.

### Compositor cost (what keeps the desktop smooth)
- **Moving the mouse does not redraw the scene.** The cursor is drawn into the backbuffer over a saved copy of what was underneath (`gfx_cursor_forget/restore/rows` in gfx.c), so a cursor-only move restores that box, draws the cursor at the new place and presents **only the affected rows** (`gfx_present_rows` → lseek on `/dev/fb0` + write; `dev_fb_write` honors the offset now and keeps its shadow copy in sync). A full repaint happens only when something really changed: a client frame, a click, the clock, or the pointer entering the panel, a menu, a window title bar or a resize grip (`window_hover_dirty`).
- **A partial write must poison the kernel's shadow, not update it.** `/dev/fb0` keeps a shadow copy of the screen so a full frame only pushes the pixels that changed. When the band under the cursor is written through the offset, writing the same bytes into the shadow looks right and is not: the wallpaper disappeared, because the next full frame then found those rows "already correct" and skipped them. The partial path writes the inverted bytes instead — the next full frame rewrites exactly those rows and still diffs everything else. Found by stepping through a filmstrip of frames, not from a single screenshot.
- **Frames are capped at 60 per second.** The mouse is polled every 2 ms, so without a cap the whole scene was rendered hundreds of times a second. Before these two changes `desktop.prg` sat at ~48% CPU just because the pointer was moving; it is ~11% now (QEMU, 1024x768, one playing video).
- **The LFB was never write-combining until `vmm_set_wc`.** `enable_write_combining` reprograms PAT1 to WC and the LFB loop in kernel.c maps with `VMM_FLAG_WC` (PWT), but the LFB sits inside the 0..4 GB identity map built from 2 MB pages, and `vmm_map_page` returns 0 on a 2 MB entry — so the flag never landed and real firmware left the LFB UC. QEMU/KVM hid it. On the laptop it showed up only once the fast frame path started writing whole windows: 16 FPS and a frozen cursor, because the copy runs inside `int 0x80` with interrupts off. `vmm_set_wc(virt, size)` patches the existing entries of any size in place (PWT=1, PCD=0, PAT bit 12 for 2 MB/1 GB, bit 7 for 4 KB), for both the identity and the DMAP alias. The boot line says `write-combining` or `uncached LFB`: if a machine's desktop is slow, read that line first.
- **A frame where only client windows changed is a fast frame** (`window_blit_committed`): `WP_COMMIT` no longer counts as "redraw everything" (`wserver_has_commits` instead), and when nothing lies over the committed windows' client areas (no higher window, panel, notification card, menu, popup or resize outline) the compositor re-blits just those areas, redraws the cursor and presents only those rows. Wallpaper, title bars and the panel are left alone. Cube at 640x480: whole system 13% CPU instead of 35–47%.
- **`WP_FRAME_DONE` goes out as soon as the client buffers are composited**, right after `window_render_all`, not after `gfx_present`. Before, game and compositor ran strictly in turn, so a frame cost both their times, and with the 16 ms cap that halved a game to 30 FPS on the user's laptop (1600x900, 4.4 ms per cube frame, still 32 FPS).
- **The cursor has its own 16 ms clock** (`last_cursor`). A cursor-only update used to spend the frame slot, so a client frame arriving right after a mouse step waited another 16 ms: moving the mouse fast dropped the game's FPS.
- Full frames skip what cannot be seen: no wallpaper and no lower windows under a maximized window (`window_covers_desktop`), no `COLOR_WIN_BG` fill under a client frame (the blit covers exactly the same rounded area).
- `/dev/fb0` partial writes mark rows in `g_fb_row_dirty` instead of writing inverted bytes into the shadow, which was a byte loop over megabytes when a whole window was presented that way.
- `ui_redraw_all(w)` (libui) says the window repaints every pixel each frame, so `ui_end` skips copying the shown frame into the other half (5 MB per frame for a full-screen game). Otherwise that copy is `rep movsq` now, not a per-pixel loop.
- **Jack polling is HDA traffic inside a syscall** (a Presence Detect trigger plus a millisecond of wait per pin), so the taskbar does it once every four seconds, never once per second — polling it while the volume popup was open produced a visible hitch exactly while dragging the slider.

### Desktop environment (Wayland-like window protocol)
- The kernel knows nothing about windows. `desktop.prg` is the compositor: it registers the IPC name `desktop` (`wserver.c`) and clients find it with `ov_lookup`.
- Protocol in `src/libs/common/wproto.h`. A client creates a shm buffer `w*h*4`, grants it to the compositor and sends `WP_CREATE`; it draws into that buffer and sends `WP_COMMIT`; it waits for `WP_FRAME_DONE` before drawing the next frame. The compositor composites straight out of the client's buffer — no copy through the kernel (the old path copied every frame twice).
- Events to the client: `WP_EV_MOUSE` (down/up/move/leave), `WP_EV_KEY` (scancode, modifiers **and** ready-made UTF-8 text — the compositor applies the layout via `src/libs/common/keymap.h`), `WP_EV_SCROLL`, `WP_EV_FOCUS`, `WP_EV_CLOSE` (the client exits by itself; after 2 s `wserver_tick` kills it), `WP_EV_COMMAND` (context-menu items such as "new folder", chosen by the `WP_FLAG_FILE_BROWSER` flag rather than by guessing from the title).
- `wserver_tick` also drops windows whose client died.
- **Single instance (XDG-style activation).** `wp_create_t.app` carries an application class (`"ovplayer"`, `"ovimage"`, `"notepad"`), set with `ui_app_id()` before `ui_open`. `ui_hand_over(app, path)` sends `WP_OPEN` to the compositor; it looks for a live window of that class, raises it and delivers `WP_EV_OPEN` with the path, answering `WP_OPENED{found}`. overFiles calls it before spawning, so opening a second file reuses the running app instead of opening another window. The client reads the path with `ui_open_request(w)` in its frame loop; overPlayer recreates its window when the new file needs different geometry (the protocol has no resize).
- Titles are truncated for the taskbar by UTF-8 sequence length taken from the leading byte. The old code treated every byte >= 0xC0 as a two-byte sequence, so the em dash (E2 80 94) was cut in half and showed up as "тА".

### libui — the app toolkit (`src/libs/libui`)
- Apps do not speak the protocol or paint widgets by hand. `ui_open` / `ui_begin` / `ui_end` wrap a frame; widgets are immediate-mode (`ui_button`, `ui_slider`, `ui_textbox`, `ui_password`, `ui_list`, `ui_checkbox`, `ui_label`, `ui_progress`), the theme is shared, and the font is CP866 8x16 with UTF-8 input (`src/libs/libgfx/font_ru_8x16.h`).
- `ui_begin(w, timeout)` blocks until an event arrives, so an idle app uses no CPU; pass `UI_WAIT` for "until something happens" or a number of ms for animation. It returns 0 once the user closes the window.
- `src/libs/common/ovos.h` is the single syscall header for userspace (64-bit returns). New apps include only it and `ui.h`; the old per-app copies of the wrappers are gone.
- An app's makefile is four lines plus `include ../../../lib/app.mk`.
- Ported: overFiles, notepad, overImages, overPlayer. `src/programs/*` (console) and DOOM/Quake still use their own wrappers and the framebuffer syscalls.
- Image parsers live in `src/libs/libgfx` next to the library that exports them, not in the apps: `png.h` and `bmp.h` (8/24/32 bit, RLE8, top-down rows). They are header-only and allocate nothing: the caller passes the output buffer. Everything with sound or motion in it belongs to `/lib/ffmpeg.ll`.

### UI font (real TrueType, parsed in the system)
- The graphical session renders text with **a real .ttf, parsed and rasterised at runtime**: `src/libs/libgfx/ttf.c` reads `cmap` (formats 4 and 12), `loca`, `glyf`, `hmtx` and `head/hhea/OS2`, turns the quadratic outlines into polygons and fills them with the nonzero rule and 4x4 supersampling; rendered glyphs land in a cache keyed by (codepoint, size) inside a static arena (no libc, no FreeType). The font file lives at `/sys/fonts/ui.ttf` — drop another .ttf there (or `make UI_FONT_TTF=...`) and the whole interface is drawn with it.
- `src/libs/libgfx/uifont.h` is the shared facade (load the file once per process, glyph lookup, substitution for missing characters, blending); `Desktop/gfx.c` and `src/libs/libui/ui.c` write their own pixel loops because one draws into the screen backbuffer and the other into the client's shm buffer. If the file is missing or broken, both fall back to the old raster 8x16 (`font_ru_8x16.h`), so the desktop stays readable.
- Composite glyphs matter: Cyrillic А is Latin A in most fonts, so `load_glyph_outline` recurses through components with their 2x2 transform — without that half the alphabet comes out blank. The font's Y axis points up while raster rows go down, so the glyph is rasterised with a negative Y scale.
- The font is proportional, so **nothing may compute positions as `chars * 8`**: `gfx_text_width()` / `ui_text_width()` give the real width (that is how the clock, the centred window title, text fields and the greeter are laid out). Where columns must line up — the notepad text area — `ui_text_mono()` draws the raster 8x16 (`UI_MONO_W`), exactly as a desktop uses a monospace font in editors. The kernel console keeps the 8x16 font too.
- Cost at 1024x768: wallpaper ~0.8 ms, taskbar with all its text ~0.2 ms, `gfx_present` ~0.9 ms per frame, so text is not what limits the frame rate (the loop idles waiting for input).

### Icons (SVG, rasterised in the system)
- Theme icons are **.svg files in `/sys/icons`** and application icons are the `ICON` resource of each `.prg`; both are rendered by `src/libs/libgfx/svg.c`: a subset parser (path `M L H V C S Q T A Z`, `rect`/`circle`/`ellipse`/`line`/`polygon`/`polyline`, `fill`/`stroke`/`stroke-width`/opacity, `transform` translate/scale/matrix) plus the same scanline rasteriser as the font, at 8x8 supersampling.
- `fill="currentColor"` means "the colour the caller asks for", and monochrome icons are rendered once in white and tinted when drawn (`gfx_icon` / `gfx_icon_draw` in gfx.c keep a cache per name and size), so the same file serves the normal, highlighted and muted states.
- Strokes are drawn by expanding every segment into a quad **plus a disc at each joint, all accumulated into one coverage pass** — filling segment by segment double-blends the joints and leaves dark spots. Three things had to be right for that to look like a circle: every piece is added with **one orientation** (`edge_add_poly` flips it by the sign of the area — otherwise a clockwise disc cancelled a counter-clockwise quad under the nonzero rule and the ring grew teeth at each joint), the contour is **closed** (the segment from the last point back to the first was missing, leaving a gap), and sin/cos are computed with range reduction (`svg_sincos` folds to a quarter angle and doubles twice — the plain Taylor series gave cos(180°) = -1.21 and bent the circle).
- Coverage is exact horizontally: each scanline span adds a full unit to whole pixels and a fraction to the two edge pixels, with 16 subsample rows vertically (4096 levels instead of 64). Curves are flattened by the length of their control polygon in device pixels, so a 16 px icon is cheap and a 128 px one is still round.
- The dock, the tray, the launcher button, window title bars and notifications use them; a program without an `ICON` resource falls back to the 16x16 mono icon it sent with `WP_CREATE`.

### Frame delivery (double buffering)
- The client's shm buffer is **twice the window**: libui draws into one half and shows the other, and `wp_commit_t.off` names the half that is ready (in pixels). The compositor composites `w->surf + w->surf_off` and only accepts an offset that fits inside `surf_cap`.
- Without it the compositor read the same half the client was drawing into. It does not redraw only on `WP_COMMIT` — dragging a window redraws on every mouse move — so it regularly caught the window right after `ui_clear`, and the video in the player flickered. `ui_end` commits, flips, and copies the shown frame into the new half, because many windows draw on top of the previous frame instead of clearing it.

### Window decorations and resizing
- `window_render_all(mx, my)` draws Breeze-like frames: **rounded corners on all four sides** (`gfx_round_rect` with a corner mask, and `gfx_blit_round` for the client's frame — the corner pixels are simply left untouched, so whatever is behind, wallpaper or another window, shows through without any alpha channel). A maximized window gets square corners, as everywhere else. A dark title bar (brighter for the active window plus a 1 px blue line under it), the icon on the left, the title centred and clamped between the icon and the buttons, and **minimize / maximize / close** on the right with a hover plate (red for close). The buttons are drawn with primitives (`gfx_line`), not glyphs.
- **Maximize needs the protocol**, because the frame buffer belongs to the client: the compositor sends `WP_EV_RESIZE{w,h}` and only remembers the wanted geometry; the client (libui, in `ui_begin` before drawing) creates a new shm buffer, grants it and answers `WP_RESIZE{shm_id,w,h}`; `window_apply_resize` maps it, drops the old one and applies the saved position. Changing `w->w/h` up front would show one frame of garbage from the smaller buffer. A double click on the title bar does the same.
- Only windows that declare `WP_FLAG_RESIZABLE` get the button: overFiles, notepad, overImages and overPlayer compute their layout from `ui_width()`/`ui_height()` every frame (the player also rescales the video to the window).
- **Dragging an edge resizes the window.** `window_edge_at` returns the edge under the pointer (5 px grip, title buttons win over the top edge), and while the mouse is held only an outline is dragged (`window_draw_resize_hint`) — the real resize goes through the same `WP_EV_RESIZE`/`WP_RESIZE` handshake on release, because reallocating the client's buffer on every mouse move would be absurd. Minimum size 220x120.

- **Pointer grab** (`WP_GRAB`, like pointer lock / SDL relative mode): only the active window gets it; while grabbed the compositor reads the unclamped mouse delta (syscall 23), sends `WP_EV_MOTION{dx,dy,buttons}` (all three buttons — normal `WP_EV_MOUSE` only carries the left one), pins the logical cursor to the window centre (so wheel and hover stay there) and hides the cursor (`GFX_CUR_HIDDEN`). Meta, activating another window, minimising or closing it releases the grab, and the client learns it from `WP_EV_GRAB`. libui: `ui_grab`, `ui_grabbed`, `ui_motion`, `ui_buttons`.
- **Cursor shapes.** `Desktop/cursors.h` holds the pack (arrow, I-beam, busy, hand, move and four resize arrows) as 16x16 pictures made of `#`/`.`/space, so they are editable by hand. `window_cursor_at(mx, my)` picks one: the compositor itself answers for window edges and corners, inside a window the shape is whatever the client asked for with **`WP_CURSOR`** (`w->cursor`), and while an edge is being dragged the shape is frozen. libui resets the shape to the arrow every frame and `ui_cursor(w, shape)` sets it for that frame — `ui_textbox` asks for `WP_CUR_TEXT` by itself.
- **A window slot is zeroed on allocation** (`slot_alloc` in window.c). It used to reset five fields, so a new window inherited `maximized`/`want_*`/`rest_*` from the client that died in that slot: after overCraft crashed maximized, the next overCraft window opened with square corners and could neither be resized nor maximized.
- **`maximized` must not be toggled in `window_apply_resize`.** It used to flip the flag on every applied resize, so one edge drag left the window thinking it was maximized: corners went square and `window_edge_at` refused to resize it again. The requester now states the result in `w->want_max` (the maximize button flips it, an edge drag sets 0), and `g_resize_edge` is cleared on release — otherwise the resize cursor stayed on screen forever.

### Desktop applications
- The GUI ships nine: overFiles, notepad, overImages, overPlayer, **overTerm** (terminal), **overTask** (task manager), **overSettings** (system settings), **overMark** (CPU stress test) and **overCraft** (`/desprogs/overCraft/`, the C++ voxel game, its own engine library and the first program folder). Each is a directory under `src/files/progs` with a four-line makefile including `src/libs/common/app.mk`. `src/files/progs/readme.md` is the guide for writing a new one (window protocol, libui, icons, resize, cursor, single instance, what the system offers and what it still cannot do).
- **overTerm is a real terminal emulator**: it opens a pseudo-terminal sized to its text area, forwards raw scancodes into it (`ov_pty_key`, releases included — layout, Shift, Backspace and echo are the TTY driver's job, as in Linux) and blits the console picture it gets back from `ov_pty_read`. The shell inside is `/sys/sh.prg`, so everything the text console has works here, `fastfetch` included. Resizing the window reopens the pty, because the console geometry is fixed at creation.
- **overTask** is the task manager: the process table from syscall 113 with owner, state and memory, refreshed every second, and "снять задачу" through `ov_kill`. **overSettings** shows system info, the timezone list (syscall 97/96), language and layouts, and the user list; root-only settings are unlocked with the same password dialog as overFiles (`ov_sudo`).
- **overMark** (`src/files/progs/overMark`) is a FurMark-like CPU burner: `burn.c` raymarches a furry torus with GCC vector extensions (4 rays per `v4`, `__builtin_ia32_sqrtps`/`minps`/`maxps`, own `vsin`; not `<xmmintrin.h>`, which pulls in `stdlib.h`), a fixed number of steps per ray so the load never lightens; `overmark.c` hands 8-row bands to the main thread and every free worker core through an atomic counter, and shows FPS, per-thread load, the CPU temperature and frequency (syscall **143 `sys_cpu_sensors`** → `cpu_temperature` in cpu.c: Intel DTS — `IA32_THERM_STATUS`/`IA32_PACKAGE_THERM_STATUS` against TjMax from `MSR_TEMPERATURE_TARGET`; AMD 17h+ Tctl through SMN 0x59800 at 0:0.0 0x60/0x64, 15h/16h at 0:18.3 0xA4), a 90 s temperature graph and an auto-stop threshold. QEMU has no sensor ("нет датчика"). `burn.c` is system-free, so it can be compiled and looked at on the host.
- **`ov_wait_u32(p, v)` waits WHILE `*p == v`** (until it changes), not until it becomes `v`: overMark's first version waited for "the next frame number" and its workers spun through the syscall, while the main thread hung on the first frame. Loop as `while (*p == seen) ov_wait_u32(p, seen, 0);` like `engine/jobs.cpp`.
- Two return-value traps bit all three apps: `sys_getpwuid` (85) and `sys_get_time` (8) return **1 on success, 0 on failure**, not 0 on success. A `== 0` check there silently shows "?" instead of the user name.
- Russian labels do not fit in byte-sized buffers: `menu_app_t.name` and the dock tooltip had to grow to 64 bytes, because "Параметры системы" is 33 bytes in UTF-8. The same goes for column padding — pad by characters, not bytes (`utf8_chars` in overtask.c).

### Taskbar dock
- The launcher button is icon-only (the `launcher.svg` icon on a rounded plate, `DOCK_X` wide), as in a Plasma dock; the layout indicator, the clock and the menus are rounded too.
- The window list in the panel is a **dock of icons** (`dock_build` in taskbar.c): pinned programs from `desktop.json` (`"pinned"`, paths separated by `;`) come first, then windows that match no pin. A running program is matched to its pin by application class (`wp_create_t.app`, set with `ui_app_id`) — that is why overFiles also calls `ui_app_id("ovfiles")` now; without it a second icon would appear next to its own shortcut.
- A running program is marked with a line under the icon (short when minimized), the hovered icon shows a tooltip with the window title, a click launches/raises/minimizes it, and **right click opens the dock menu**: pin/unpin (writes `desktop.json` through `settings_save`) and close the window. Right click anywhere on the panel goes to `taskbar_ctx_at` (desktop.c), so the menu belongs to the panel, not to the desktop.
- Icons and names of programs that are not running come from their `.prg` resources (see "Program resources" above); a running window is matched to its pin by executable path first, then by class.

### Media formats
- **`.ll` limits** were raised for the full FFmpeg: slot 256 MB, image 48 MB, memory 240 MB. A library larger than `kernel_temp_buf` (4 MB) is read into pages allocated for the occasion and released right after — before that the read was silently truncated and the header check rejected the file as broken.
- `src/libs/libgfx/png.h` is a self-contained PNG decoder: own DEFLATE (fixed + dynamic Huffman, stored blocks), all five row filters, color types 0/2/3/4/6, depths 1–16, palette `tRNS`, IDAT split over several chunks. Adam7 interlace is refused (`PNG_ERR_INTERLACE`). It allocates nothing — the caller passes the ARGB output buffer and a scratch buffer of at least `h * (1 + bytes_per_row)`.
- The PNG decoder is integer-only; that is no longer forced, but it keeps the decoder cheap and exact.
- overImages loads BMP and PNG through one path: both are decoded into `s_argb` at load time and the drawing code only scales and alpha-blends. Format is detected by file signature, not by extension. Error codes of the three layers (loader `-30..`, BMP `-20..`, PNG `-1..-10`) must not overlap — they share one `switch` in `err_text`.
- `overFiles/ext.h` maps extensions to a kind (`FILE_KIND_*`, drives the icon), a Russian type label and an action. An action is only assigned to formats our apps can actually open (`.bmp`/`.png` → viewer; `.mp4`/`.mov`/`.mkv`/`.webm`/`.avi`/`.m4a`/`.mp3`/`.wav`/`.aac`/`.h264` → player, i.e. what FFmpeg is built with); everything else reports "нечем открыть" rather than opening an empty window. The kind is cached in `s_kind[]` during `reload()`, because `ext_get_kind` reads the DPRG header of `.prg` files from disk.
- Test assets `src/files/image/*.png` and `src/files/sound/*.mp3` are copied into the image and the FAT partition depends on `IMAGE_ASSETS`, so changing one rebuilds the image.
- An app that needs a `src/libs/libgfx/*.c` file lists it in `LIBSRCS` in its makefile (the compositor pulls in `ttf.c svg.c`); app.mk compiles those into `build/lib_*.o`. The DE apps need none of it any more — they bind the libraries instead.
- **The decoders are gone from the tree.** `src/lib/{mp3,mp4,h264,h264_decode,aac}.c` and their tables were deleted when real FFmpeg landed: everything they did, `/lib/ffmpeg.ll` does better (HE-AAC with SBR, MKV/AVI, libswscale). They are in the git history if a detail is ever needed; the notes on their internals went with them. `wav.h` went too, so `libgfx.ll` no longer touches audio at all.
- **Decoded video frames sit in a queue** (`s_vq` in avshim.c, up to 8 frames, fewer for a large picture). There used to be exactly one "next" frame, and while it waited for its time `avcodec_receive_frame` was not called at all: libavcodec's output queue filled up, `avcodec_send_packet` answered EAGAIN and the **packet was dropped**. For H.264 that is a hole in the stream — nothing decodes until the next key frame, so the picture froze on the first frame while the sound played on. Dropping a decoded frame is fine (it is a skipped frame), dropping a packet is not, so now the frame queue overflows instead of the decoder, and EAGAIN means "take the frames first, then resend".
- overPlayer plays whatever `/lib/ffmpeg.ll` was built with (MP4/MOV, MKV, AVI, MP3, WAV, raw AAC and H.264). The window is sized to the picture and the layout is recomputed from `ui_width()`/`ui_height()` every frame; frames are picked by presentation time, scaling and YUV->RGB are libswscale's job.
- `src/libs/ffmpeg/limiter.h` is a look-ahead peak limiter (one 128-sample block of delay, gain ramped over the block, slow release) applied in `avshim.c` to FFmpeg's float output before it becomes int16. Web audio is routinely louder than full scale — ffmpeg's own decode of this file peaks at 1.30 — so a plain cast clips. With the limiter the same file produces zero clipped samples.
- **Opening PCM takes the rate in one argument and channels+bits packed in the next** (`syscall 70`, sub-command 7: `hda_pcm_open(rate, channels, bits, pid)`). The player used to pack all three into one argument, so the driver saw `channels = 0` and answered -3 — "Ошибка звука" with no sound at all. If audio goes silent, check that call first.
- **A codec verb waits 2 ms, not 50.** `hda_xfer` used to spin for 50000 µs before falling back to Immediate Command, and jack polling runs from the compositor's own loop — one unanswered verb froze the whole desktop for 50 ms. The taskbar also polls the jacks every four seconds now instead of every second (immediately while the sound popup is open).
- **The audio queue is serviced by the kernel timer** (`hda_tick`, called from `timer_isr_handler`). It used to be refilled and drained only inside the owning program's syscalls, so as soon as the player went quiet — pause, or just the user switching to a TTY — `pcm_update()` stopped zeroing what the DMA had already played, the controller reached the end of the ring and played it again: that is the "го-го-го" repeat on pause. `s_mix_busy` keeps the timer out of the mixer while a syscall is in it.
- **"Speakers" must not mute the only real output.** `apply_routing` counts only pins the BIOS marked as connected: a laptop can have a "Speaker" pin with nothing behind it while the real speakers hang off line-out, and the old check (does a pin of this class exist at all) then enabled the dead one and muted the live one — the button looked broken. The sound popup also shows where the driver actually routes the sound (syscall 70 sub-command 17), so a switch that did nothing is visible.
- **The test tone is topped up from the kernel timer** (`tone_feed`, called from `hda_tick`). It used to be written out in one go, about 300 ms worth, and if the stream restarted in that moment — picking an output does exactly that — nothing was heard at all.
- **The test tone is an ordinary mixer voice** (`TEST_TONE_OWNER`), not a takeover of the hardware stream. It used to grab the whole stream, so picking an output device while a video was playing produced no sound at all, and stopping the tone (`sys_audio` sub-command 5) silenced the player as well. That sub-command now closes only the tone's voice.
- **Audio is mixed in the driver** (`hda.c`): each process gets a voice (`PCM_VOICES`, found by pid) with its own ring in the output format and its own linear resampler; `mix_pump` sums them into the single hardware ring. Before that `hda_pcm_open` stopped whatever was playing, so a second player killed the sound of the first. Every `hda_pcm_*` call takes the owner pid (`user_mode.c` passes `caller->pid`), the voice of a dead process is reclaimed on the next open, and the hardware stream stops when the last voice closes. Position and `drained` are per voice through `last_wr_pos` (the hardware ring position after that voice's last mixed frame) — the mixer must **not** pad silence when every voice is empty, otherwise the queue never drains and the player hangs on "Играет". `apply_gain` saturates, because a sum of voices leaves int16.
- `hda_pcm_flush` (seek/pause) can only clear the hardware ring when it is the single voice; with several, up to `ring_target()` of already mixed audio still plays, which is why the target drops from ~170 ms to ~64 ms as soon as a second voice appears.
- **No libc in programs either**: a plain struct assignment (`out->video = tmp;`) compiles to a `memcpy` call that does not link. Copy structs with an explicit byte loop in anything that is not linked against libc (programs, `src/lib`, the libraries themselves).
- **A big struct must not go on the stack of a Ring 3 program.** The program stack is 512 KB; a parser that kept one container-track struct as a local blew it and died with a #PF right after start. Make such things `static`. When a program faults, map the reported RIP to a function with `nm -n <app>.elf` and compare RSP against `PRG_STACK_TOP - stack_size`.

### C++ programs, program folders and the 3D engine (`src/libs/cxxrt`, `overCraft/engine`)
- **`.cpp` files go into `SRCS` like `.c`**: `app.mk` builds them with `g++ -std=c++17 -ffreestanding -fno-exceptions -fno-rtti -fno-threadsafe-statics` and links `src/libs/cxxrt/cxxrt.o` by itself whenever there is C++ in the program. `CXXLIBSRCS` takes `.cpp` files from `src/libs`. No STL, no exceptions, no RTTI — the language itself (classes, templates, operators, lambdas) is all there is.
- **cxxrt** is the minimum the language demands from a runtime: `operator new/delete` on its own heap (address-ordered free list that coalesces neighbours; `new` exits with 12 on OOM since there are no exceptions), `__cxa_pure_virtual`, accepting-and-ignoring `__cxa_atexit`, and `memcpy/memset/memmove/memcmp` (g++ calls them for struct copies; `rep movsb/stosb` because GCC turns a plain loop back into a `memcpy` call). In a program the heap grows on brk (256 KB steps) — so a C++ program must not load `libc.ll`. Built with `-DCXXRT_ARENA_KB=N` (inside a `.ll`) the heap is a static array instead: brk belongs to the program.
- **Global constructors** run from `ovcxx_init()`, which walks `.init_array` between `__init_array_start`/`__init_array_end` from the program's linker script (see `overCraft/overcraft.ld`). The symbols are weak, so a script without them silently means "no constructors" — copy that script. In the `.ll` variant this code is compiled out: a weak undefined symbol there became an absolute `R_X86_64_32S` zero, which `elf2ll.py` (rightly) refuses; `app.mk` also refuses a `.ll` that has an `.init_array`.
- **Program folders** (like macOS `.app`): `/desprogs/<Name>/` with one `.prg` inside is a program; `taskbar_refresh_menu_apps` looks one level into `/desprogs` directories (menu paths are 96 bytes now, `MAX_MENU_APPS` 16). Next to the `.prg` live its own `.ll` and `resources/`; the program finds its folder from its executable path (`ov_proc_exe(ov_getpid())`, `oe_game_dir`). `app.mk` builds a program's own library from `LL_TARGET`/`LL_SRCS`/`LL_ARENA_KB` (PIE, `--no-relax`, `lib.ld`, `elf2ll.py`); the root Makefile copies the folder (`OVCUBE_*`; the `.ll` target has an empty recipe after the `.prg` so make re-stats it).
- **ovengine** lives in the game (`src/files/progs/overCraft/engine`) and ships as `/desprogs/overCraft/ovengine.ll`. The boundary is C (`extern "C" oe_*`): `.ll` symbols are looked up by name and C++ names are mangled. `ovengine.h` holds the shared types (`ov::Vertex/Face/Mesh/Light`, `math3d.h`) — both sides compile the same header, so layouts agree — and the `oe_*` declarations only under `OVENGINE_BUILD`; the game includes `ovengine_ll.h` (`oe_bind(dir)` with a version check, then the `ov::Renderer` wrapper). What belongs to the game stays in the game: world, meshes, camera, input. The binding tables `g_ui` (libui_ll.h) and `g_oe` are `__attribute__((weak))` definitions, not `static`: a program of several .cpp files must share one table, otherwise only `main.cpp`'s copy is bound and the other files call through null pointers. Textures are PNGs in `resources/` decoded by `libgfx/png.h` inside the engine (power-of-two sizes up to 2048, alpha ignored for now).
- **Engine v2+ (now OE_VERSION 3) is a deferred, multi-core renderer** (`engine/renderer.cpp`, CPU only, like Quake): `oe_begin(camera)` → `oe_draw(mesh, model)`… → `oe_end()`. `oe_draw` only records; `oe_end` runs three parallel passes on the engine's `JobPool` (`engine/jobs.cpp`: one worker per free core via `ov_worker_start`, the main thread works too and then waits with `ov_wait_u32`): (1) geometry per mesh — MVP, near-plane clipping `z >= -w`, screen-space back-face culling (front faces are CCW; with screen Y down that is negative area), off-screen rejection; triangles go into one frame buffer (`kTriCap` 160k, threads reserve blocks of 64 with one atomic add); (2) binning into 16-row bands — count per (part, band), prefix on the main thread, fill; (3) per band: sky gradient + z clear, then its triangles, then the nearest-pixel upscale when the world is drawn below 100 %. Per triangle: each row's span comes from the edge equations (no bbox walk), every attribute (1/w, u/w, v/w, shade) is a screen-space gradient advanced by addition, perspective is divided only every 16 pixels with 16.16 fixed-point u/v in between (Quake), and a triangle whose w varies by < 8 % takes a fully affine path with no division per row at all. z-buffer of 1/w, nearest texel with wrap (UV > 1 repeats, which greedy meshes rely on), per-vertex `shade` for AO, distance fog to the row's sky colour. **The affine path must step its own gradients per row** (`gu/gv/gf.v += .dy`): it once did not, every row started at the same texel, and distant faces turned into vertical streaks on the user's laptop while the bench camera (close up, perspective path) looked fine — check far views too. Its threshold is the w spread **times the texel span** of the triangle (≤ half a texel), not a flat 8 %: a greedy quad repeats the texture up to 16 times, so 8 % already slid it by whole texels. **Transparency** comes from the PNG alpha (`addTexture(..., with_alpha)` picks `TEX_OPAQUE`/`TEX_CUTOUT` for 0/255 only/`TEX_BLEND` for anything between); `bandJob` rasterises opaque and cutout triangles first, then blended ones in reverse submission order (far to near, since the game submits near to far) with z-test but no z-write, except fully opaque texels such as the glass frame. `oe_texture_add` stays opaque (0xRRGGBB). Bands never overlap, so there are no locks. `oe_parallel(count, fn, ctx)` gives the game the same pool. `FrameStats` reports per-thread busy share (overCraft's F3 screen shows it). `math3d.h` has its own `sin` (range reduction) and `sqrtss`: programs have no libm.
- Every allocation the passes need happens on the main thread before them (scratch per thread, bins, counters): code on a worker core must not allocate. The engine's heap is a 64 MB arena (`LL_ARENA_KB`).
- **Frame buffers are sized for the whole window, not for the current percentage** (`setTarget`): depth, the hand's own depth (`odepth_`) and the dynamic-resolution colour buffer are allocated once per window size, old ones freed first. Dynamic resolution moves the percentage every frame, and reallocating three multi-megabyte buffers on every step up left holes the first-fit cxxrt heap could not reuse — the maximized game on the laptop died with code 12. F3 now prints both heaps (`oe_memory`, engine v6: used / total / largest free block; `ov_heap_largest_free` in cxxrt): a largest free block of a couple of MB is the warning sign. `tools/ovcraft_bench/run.sh mem` replays window sizes and percentages under the real cxxrt allocator (1920x1000: ~34 MB, 14 MB largest free).
- The overlay (hand) pass has **its own z-buffer**: clearing the world's z for the whole band, as v4 did, made the block outline (which tests against `oe_depth`) show through blocks on every row the hand touched; now the hand's pixels are only marked "nearest" (1e30) in the world's z.
- `tools/ovcraft_bench/run.sh sim [frames]` runs the whole game (world, player, pigs, items, inventory, icons, hand, renderer) with scripted input under ASan+UBSan: 8000 frames, 1300 broken blocks, 160 pigs, no memory errors. It also paints the sky magenta and counts isolated sky pixels (`HOLES=out.ppm` keeps the worst frame; `DBGF/DBGX/DBGY` dumps the triangles under a pixel through `OE_DEBUG`) — the ones found so far were real gaps between leaf blocks, not raster cracks. Span ends are computed in double anyway.
- `ui_pixels(w)` flips between the two halves of the shm buffer every frame, so `setTarget` is called every frame. Animation uses `ui_begin(w, 0)`: `ui_begin` already waits for `WP_FRAME_DONE`, which caps the program at the compositor's 60 FPS.
- **overCraft** (`src/files/progs/overCraft`): `config.h` (every tunable), `blocks.h` (block table + texture list + hotbar), `world/` (`noise.h` hash/value noise/fbm, `generator.*` terrain + beaches + snow + caves + trees from coordinates and `cfg::SEED` only, so chunks generate in any order on any core and agree at borders, `mesher.*` visible faces with per-vertex AO and AO-aware quad diagonal, greedy-merged per slice and grouped by face direction, built from a padded copy of the chunk and its 8 neighbours, `world.*` a (2L+1)² slot grid indexed by chunk coords mod D, per-frame generation and meshing through `oe_parallel`, edits list re-applied on regeneration, frustum culling per 16-high section, DDA raycast), `game/` (`input.h` key state from `ui_raw_keys`, `player.*` fixed-step physics with per-axis AABB collision, walk/sprint/sneak/jump/swim/fly, `hud.*` crosshair, hotbar, F3 stats, block outline). Section mesh buffers grow only on the main thread: a section that does not fit records `need_v/need_f`, the main thread grows it and the chunk is meshed again in the same frame. `tools/ovcraft_textures.py` regenerates the 16x16 PNGs.
- **What the frame cost was made of** (the laptop showed 34 FPS, 4 threads at ~95 %, raster 21.9 ms): mostly tiny triangles and short rows, not pixels — 68k triangle setups and 265k rows with two divisions each, 1.75M pixels walked and 1.28M written for a 655k-pixel frame. The fixes, in the order they paid off: `1/a` per triangle and a `1/n` table instead of divisions per row and per 16-pixel piece; **greedy meshing** in `mesher.cpp` (faces with the same texture and uniform AO merge into one rectangle per slice; non-uniform AO stays per face so shadows do not smear); **chunks drawn near to far** (`World::order_`), which halves written pixels because the z-test rejects hidden ones before the texel fetch; **per-direction face groups** (`SectionMesh::dir[6]`), so a section's top faces are not even submitted when the eye is below it (submitted 302k → 181k). Host bench, one thread, 1024x640: raster 20.6 → 12.4 ms, geometry 8.2 → 3.9 ms.
- **Dynamic resolution** (`cfg::DYNAMIC_RES`, `RES_MIN`..`RES_MAX`, `FRAME_BUDGET`): `oe_set_target(..., percent)` renders the world into an internal buffer at that share of the window, upscaled per band through a column map; the HUD stays full resolution. `main.cpp` smooths the frame time and moves the percentage by 1 % a frame. On `-smp 1` in QEMU the game holds 60 FPS at ~82 %.
- **Engine v4** adds `oe_draw_ex(..., OE_DRAW_OVERLAY)` and `oe_texture_pixels`. Overlay meshes are given in eye space and projected with `Camera::overlay_proj` (no view matrix, its own FOV, so the sprint FOV does not stretch the hand); `bandJob` rasterises the world first, then clears the band's z and draws the overlay triangles (`STri.valid & STRI_OVERLAY`). That is the whole first-person hand: no special case in the game beyond a matrix.
- **Engine v5** adds `oe_depth` (the last frame's z-buffer, 1/w, overlay included): `hud::outline` tests every pixel of the block outline against it with a 2 % margin, so the outline no longer shows through nearer blocks or the hand.
- **Gameplay layer** (all in `game/`): `physics` (box vs world, shared by player, mobs and dropped items; sneak edge guard via `ground_below`), `player` (survival by Minecraft's rules — 20 health/food, saturation before food, exhaustion 4 → one point, regen at food ≥ 18, starvation, fall damage over 3 blocks, 15 s of air; sneak lowers the eye and the box and refuses to stand up under a ceiling; sprint by Ctrl or double W, broken by a wall or food < 7), `inventory` (36 slots, 0..8 hotbar; the screen keeps the pointer **grabbed** and draws its own cursor, because a normal `WP_EV_MOUSE` carries only the left button and the screen needs right-click and Shift), `icons` (block icons are an orthographic 45°/30° cube rasterised per pixel from the engine's texture pixels, cached per size), `model` (`.mdl` text models: `texture W H`, `part name px py pz`, `box x y z w h d u v`, pixels, Minecraft box UV layout, so a real 64x64 skin fits; two face sets per part — normal and a red copy of the skin for the hurt flash, no tint in the engine), `shapes` (block cubes, items extruded one pixel thick like the original, crack cubes), `entity` (fixed slot array, pig AI wander/idle/look/panic, knockback, death tilt, drops, item entities with Minecraft's pickup box = player box grown by 1/0.5), `hand` (first-person arm/held item, bob, swing, equip, eat). Data tables: `items.h` (ids ≥ `ITEM_FIRST` = 64; below that an item id is a block id), `entities.h` (type → model, skin, box, health, drops), `blocks.h` gained `hardness` (seconds by hand) and `drop`. Texture order at the engine: blocks, items, 10 crack stages, then skins (loaded by `Entities::init`). `tools/ovcraft_textures.py` also paints the skins, the item and the cracks; the root Makefile copies `resources/` recursively (`mcopy -s`).
- `tools/ovcraft_bench/run.sh models out.ppm` renders models, items and the hand with the real code (`SCENE=models|hand|held|item`, `SWING=`, `CAM`/`YAW`/`PITCH`); `fake/engine/ovengine_ll.h` is an `ov::Renderer` straight over `Rasterizer`, so game modules compile on the host unchanged. Tune hand/model matrices there, not through QEMU (its relative mouse moves are scaled ~2x and imprecise).
- `tools/ovcraft_bench/run.sh [w h [frame.ppm [percent]]]` builds the real renderer, generator and mesher on the host with a stub `ovos.h` (one thread), loads the game's real PNGs, and prints geometry/raster ms for a camera set by `EYE=x,y,z YAW= PITCH=` (`GLASS=x,y,z` adds a glass wall, `NOWATER=1` hides water, `FINDWATER=1` lists water columns) — that is where the numbers above come from; there is no profiler inside overOS, and QEMU timings jitter too much to compare small changes.
- Measured in QEMU/KVM, maximized 1024x694, view radius 5, 4 threads: 7 ms per frame (geometry 2.3, raster 4.6), 40k submitted / 24k drawn triangles.
- **`compile_commands.json` is regenerated by every `make`** (`tools/gen_compile_commands.py` walks `src/files/progs/*`, `src/libs/*` and picks `g++` + C++ flags for `.cpp`, the `.ll` flags for a program's `engine/`). The stale one (still pointing at the removed `src/lib`, no C++ at all) is why the editor flagged `extern "C"` in `cxxrt.h` while the build was clean. `clangd --check` lines "tweak: ... FAIL" and "Failed to resolve URI" are clangd's own noise and count into its "N errors" summary; real diagnostics look like `E[...] [diag_name] Line N:`.

### Shared libraries (`.ll`)
- **`src/libs/` is now the whole of userspace-shared code**, one directory per library: `common/` (`ovos.h`, `wproto.h`, `keymap.h`, `app.mk` — what everyone includes), `libc/`, `libm/`, `libgfx/` (its `.c` plus `png.h`, `bmp.h`, `ttf.c`, `svg.c`, `uifont.h`, the console font), `libui/` (its `.c` plus `ui.c`/`ui.h`), `ffmpeg/`, and the shared `lib.ld`. Each library folder holds the library's source **and** its `<name>_ll.h` binding header. `src/lib/` is gone — one `lib`/`libs` pair was pure confusion. `src/libs/readme.md` explains the format, the layout and how to add a library.
- A program includes headers by directory (`#include "libui/ui.h"`, `"libgfx/png.h"`, `"ffmpeg/ffmpeg_ll.h"`), while `common/` is also on the include path so `#include "common/ovos.h"` and the bare `"ovos.h"` both work. `-I src/libs -I src/libs/common` is in `CFLAGS_PROG`, `CFLAGS_LL`, `app.mk` (now `src/libs/common/app.mk`) and the compositor's makefile.
- `.ll` is the overOS equivalent of `.so`/`.dll` and the loader is `src/kernel/lib_loader.c`. The file carries the image, a relocation table (`R_X86_64_64`/`RELATIVE` offsets) and an export table (name → offset). The kernel maps it into **the calling process's** address space at `LIB_BASE` (`0x6000_0000_0000`, 64 MB per slot, 16 slots per process), copies the image, zeroes the bss, adds the base to every relocation cell, and copies the symbol/string tables into the pages right after the image — that way the loader needs no kernel heap. `lib_sym` only returns addresses inside that slot, so a process tampering with its own tables can only hurt itself.
- Syscalls: `119 lib_open(path)` (checks X permission), `120 lib_sym(lib, name)`, `121 lib_close(lib)`. Userspace wrappers and `OV_BIND` live in `src/libs/common/ovos.h`.
- There is **no import**: a library resolves nothing from outside and talks to the kernel through `int 0x80` itself. `elf2ll.py` refuses to pack a library with any undefined symbol, which is what keeps the format free of a dynamic linker. That is why `libui.ll` carries its own copies of `ttf.c`/`svg.c` although `libgfx.ll` has them too.
- `fork` duplicates the table entries (`lib_fork`) because the pages are copied with the address space and keep the same VA; `execve` and process exit drop them (`lib_release_pid`). Without that the child's slots looked free and the next library would have been mapped over the inherited copy.
- Shipped: `/lib/libc.ll` (mem*/str*/ctype, atoi/strtol/itoa, malloc/free/calloc/realloc on `brk`, qsort/bsearch, rand, snprintf/printf), `/lib/libm.ll` (double precision, verified against glibc at ~2e-15 relative error), **`/lib/ffmpeg.ll`** (real FFmpeg, see below), `/lib/libgfx.ll` (PNG and BMP, the TrueType rasteriser and the SVG rasteriser) and `/lib/libui.ll` (the whole toolkit). A program that loads libc must not move `brk` itself — the break is shared.
- **`/lib/ffmpeg.ll` is the system's "ffmpeg"**: a program opens a file (`av_open`), gets `av_info_t`, pulls ready PCM (`av_audio_read`) and ready pictures (`av_video_decode_until` + `av_video_blit`), and knows nothing about containers, reference-frame buffers or resampling. That is why the player is 9 KB of code and 64 KB of BSS. `/programs/avtest.prg` is the regression test (binds the library, opens a file, decodes frames, blits a picture and checks the audio peak).
- A library's BSS counts against **`LIB_MAX_MEM` (56 MB)**, not the 8 MB image limit, and `LIB_SLOT_SIZE` is 64 MB: ffmpeg.ll asks for 49 MB (3 MB of image, a 40 MB heap and FFmpeg's own tables). Both limits were hit the first time it was loaded (`lib_open` returned ENOEXEC from the old 8 MB check on `mem_size`).
- **A `.ll` may contain a GOT.** `elf2ll.py` walks `.got`/`.got.plt` and adds every non-zero cell to the relocation table — with a base-0 image such a cell is just another absolute address inside the image. Real FFmpeg needs this: it reaches its tables through the GOT. The link must then use **`--no-relax`**, because when the output is not PIE the linker happily turns those GOT loads into absolute 32-bit addresses (`R_X86_64_32S`), and the library lives at `0x6000_0000_0000`, which does not fit in 32 bits. `lib.ld` places `.got` before `.bss` on purpose, so the cells are inside the file part of the image.
- The DE apps use the shared toolkit: `USE_LIBUI := 1` in the app makefile drops `ui.o` from the link, the app includes `libui/libui_ll.h` after `ui.h` and calls `libui_bind()` first thing in `main`. The binding header is **generated from the prototypes in ui.h** and `#define`s each `ui_*` name to a field of a pointer table, so call sites stay unchanged. Sizes after the move: ovplayer 146 → 9 KB, ovfiles 37 → 21 KB, ovimage 34 → 9 KB, notepad 25 → 9 KB.
- Multi-source libraries go through the `LL_RULE` macro in the Makefile (name + list of `.c`), so adding one is two lines.
- Traps that cost accuracy in libm, all caught by comparing with glibc on 20k points: the last Taylor coefficient of `exp` must be `1/k!` of the **last** term (1/10! not 1/9!, else the error is 1e-11), `atan` needs more than one reduction node (one node left |a| ≤ 0.414 and 5e-9 of error; three nodes give 2e-16), `tanh` must go through `expm1` (the `(e-1)/(e+1)` form loses almost every digit near zero) and `acos` through `atan` near ±1.
- Regression: `/programs/lltest.prg` (`src/programs/lltest.c`) exercises the heap, strings, sorting and two dozen math functions against host-computed references; `lltest heap` runs only the allocator loop.

### Real FFmpeg (`/lib/ffmpeg.ll`)
- **The SIMD kernels are built** (`--enable-x86asm`, nasm): on the test clip (H.264 852x480) decoding goes from 790 ms to 527 ms for 200 frames, and libswscale — which runs on every frame the player shows — gains more than that. `FFMPEG_ASM=0 make libs` falls back to the plain C build.
- **Only SSE is ever used, and that is on purpose**: the kernel sets `OSFXSR` but not `CR4.OSXSAVE` (entry_kernel.asm), so `CPUID.1:ECX.OSXSAVE` is 0, FFmpeg's own check rejects AVX and picks SSE paths. That matches the context switch, which saves 512 bytes with `fxsave` — enough for xmm, not for ymm. Enabling AVX means `xsave`/`xrstor` in switch.asm first, otherwise two tasks would silently corrupt each other's upper registers.
- The asm references the FFT tables that `01-tx-tables.patch` cut out, so `02-tx-x86-maxlen.patch` lowers the x86 codelets' `max_len` to 131072 and `ffsys.c` defines four one-element stubs for the symbols the linker still wants (the code that would read them is unreachable).
- The library is **upstream FFmpeg 7.1** (libavformat + libavcodec + libswscale + libswresample) built for overOS, not a wrapper around our own decoders. `tools/build_ffmpeg.sh` does the whole thing: unpack `src/libs/ffmpeg/dist/ffmpeg-7.1.tar.xz` (downloaded once if missing) into `build/ffmpeg`, apply `src/libs/ffmpeg/patches/*`, build the sysroot, cross-configure, compile, link and pack into `.ll`. `make` runs it through the `build/ffmpeg.ll` rule; there is no fallback any more: our own decoders were deleted, because FFmpeg does everything they did and more.
- **`src/libs/ffmpeg` is the sysroot**: `include/` holds the headers overOS never had (`stdio.h`, `stdlib.h`, `string.h`, `math.h`, `time.h`, `errno.h`, `unistd.h`, `fcntl.h`, `sys/*`), and `ffsys.c` implements them — heap, `strtod`/`strtoull`, `sscanf`, file I/O over the kernel syscalls, `gmtime_r`/`mktime`, and the handful of math functions `libm.c` lacks (`cbrt`, `scalbn`, `rint`, `sincos`). `libc/libc.c` and `libm/libm.c` are compiled into the same library, so there is still no libc in the system — only this one, inside this one library.
- `src/libs/ffmpeg/ovcc` is the compiler wrapper: `-ffreestanding -nostdinc` with the sysroot, and at link time `libffsys.a` plus `-Wl,-e,main`. That is what makes `./configure` honest — its link tests only find functions overOS really has, and everything else FFmpeg replaces with its own code. The build is configured `--disable-everything` plus H.264, AAC, MP3 and PCM decoders, the mov/mp3/wav/aac/h264/matroska/avi demuxers, no network, no protocols, no threads, no asm, no iconv.
- **FFmpeg's heap is its own**, a 40 MB static pool inside the library (`ffsys.c`), not `brk`: the break belongs to the process and `libc.ll` already manages it, so two allocators on one break would corrupt each other. A 4K video with a deep DPB can exhaust the pool; `av_open` then returns "не хватило памяти" instead of dying.
- The file is read through an `AVIOContext` straight on a kernel descriptor (`io_read`/`io_seek` in `avshim.c`), so nothing is slurped into memory any more — and that needed a real **`lseek` (syscall 19)**, which the kernel simply did not have. `vfs_sys_lseek` asks the FAT driver for the size on `SEEK_END`, because a VFS node is built on the fly and its `size` field is always 0.
- `src/libs/ffmpeg/patches/01-tx-tables.patch` cuts libavutil's FFT tables at 131072 points. They are declared up to 2097152 in three variants, which is ~20 MB of `.bss` that the loader faithfully commits on every `lib_open`; no codec of ours goes above 2048.
- What the port buys: **HE-AAC (SBR + parametric stereo) plays in full** instead of its 22 kHz AAC-LC core, MKV and AVI open, scaling goes through libswscale (bilinear) instead of nearest-neighbour, and the formats are now FFmpeg's business rather than ours. What stays ours: the window, the audio output, and `limiter.h` on the float output before it becomes int16 — FFmpeg decodes above full scale just as before.
- The `av_*` API did not change, so overPlayer was not touched. `av_video_blit` now clamps its rectangle to the target buffer instead of refusing to draw.

### Modules
- `stress.sys` wakes the other cores with code assembled from `src/modules/asm/ap_burn.asm` (`tools/bin2h.py` → `build/ap_burn.h`), not with opcodes typed into C. The full long-mode bring-up (`src/modules/asm/smp_trampoline.asm`) sits next to it, unused and no longer linked into the kernel.

### On-disk layout (built by the Makefile into the FAT32 partition)
`/sys` (KERNEL.BIN, login.prg, sh.prg, logo/wallpaper bmp, `fonts/ui.ttf`, `icons/*.svg` — theme icons only), `/utils` (*.sys), `/lib` (*.ll), `/programs` (*.prg, DOOM/, Quake/), `/autostart/desktop.prg`, `/desprogs` (DE apps; a subfolder with a `.prg` is a program folder, e.g. `overCraft/` with `ovengine.ll` and `resources/`), `/configs/desktop.json`, `/media` (empty; removable volumes appear in it at runtime).
