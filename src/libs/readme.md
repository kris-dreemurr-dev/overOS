# Разделяемые библиотеки overOS (`.ll`)

Этот каталог — всё, из чего собираются файлы `/lib/*.ll` в образе. Если ты ищешь,
где лежит код какой-то библиотеки, он здесь, в папке с её именем.

## 1. Что такое `.ll`

`.ll` (linked library) — то же, чем `.so` для Linux и `.dll` для Windows: код,
который не вкомпилирован в программу, а подключается во время работы.

Зачем это нужно: декодеры видео, тулкит окон и libc нужны сразу нескольким
программам. Если линковать их в каждую, одно и то же лежит в образе по пять раз
и занимает память пять раз. Поэтому код лежит в одном файле, а программы берут
из него функции по именам.

Работает это так:

1. программа открывает библиотеку — `ov_lib_open("/lib/libui.ll")` (сисколл 119);
2. ядро (`src/kernel/lib_loader.c`) кладёт образ **в адресное пространство этой
   самой программы**: `LIB_BASE` = `0x6000_0000_0000`, по слоту 64 МБ, до 16
   библиотек на процесс. Копирует образ, обнуляет `.bss` и **прибавляет базу ко
   всем ячейкам из таблицы релокаций** — поэтому библиотеке всё равно, по
   какому адресу её положили;
3. программа спрашивает адрес символа по имени — `ov_lib_sym(h, "ui_button")`
   (сисколл 120) — и вызывает его как обычную функцию;
4. `ov_lib_close` (121) освобождает слот; `fork` отдаёт ребёнку те же образы,
   `execve` и выход из программы освобождают слоты сами.

Это модель `dlopen`/`dlsym`, а не динамического компоновщика: на этапе сборки
программа про библиотеку не знает ничего.

**Главное правило формата: у библиотеки нет импорта.** Она не может позвать
функцию ни из программы, ни из другой `.ll`. Всё, что ей нужно от системы, она
делает сама через `int 0x80` (обёртки в `src/lib/ovos.h` — заголовочные, они
встраиваются). Упаковщик `tools/elf2ll.py` отказывается собирать библиотеку, в
которой остался хоть один неразрешённый символ. Отсюда следствие, которое
выглядит как дублирование, но является осознанным: `libui.ll` несёт **свои
копии** `ttf.c` и `svg.c`, хотя они же есть в `libgfx.ll` — импортировать их
библиотека не может.

## 2. Что лежит в каталоге

```text
src/libs/
├── lib.ld              общий скрипт компоновки: база 0, порядок секций
├── readme.md           этот файл
├── libc/
│   ├── libc.c          сама библиотека: mem*/str*, числа, куча, qsort, printf
│   └── libc_ll.h       заголовок подключения для программы
├── libm/
│   ├── libm.c          математика в double (sin, exp, pow, ...)
│   └── libm_ll.h
├── libgfx/
│   ├── libgfx.c        обёртки: PNG, BMP (сами разборщики — src/lib/png.h, bmp.h)
│   └── libgfx_ll.h
├── libui/
│   ├── libui.c         таблица указателей на весь тулкит (src/lib/ui.c)
│   └── libui_ll.h
├── cxxrt/              рантайм C++ (не .ll: собирается внутрь программы или её .ll)
│   ├── cxxrt.h         ovcxx_init, ov_malloc/ov_free, размещающий new
│   └── cxxrt.cpp       куча (brk у программы, статическая арена у .ll), new/delete, mem*
└── ffmpeg/             порт настоящего FFmpeg, подробности в разделе 5
    ├── av.h            интерфейс библиотеки: av_open, av_audio_read, ...
    ├── avshim.c        прослойка: av_* поверх libavformat/libavcodec
    ├── ffsys.c         «libc» для FFmpeg: куча, строки, файлы, время
    ├── limiter.h       пиковый лимитер на выходе звука
    ├── ffmpeg_ll.h     заголовок подключения для программы
    ├── include/        сисрут: stdio.h, stdlib.h, string.h, math.h, sys/*
    ├── ovcc            компилятор-обёртка (gcc + сисрут, без хозяйской libc)
    ├── patches/        заплаты к исходникам FFmpeg
    └── dist/           архив исходников FFmpeg (качается один раз)
```

В каждой папке ровно два вида файлов:

* **исходник библиотеки** (`libc.c`, `libui.c`, ...) — он компилируется в `.ll` и
  живёт в Ring 3 внутри чужого процесса;
* **заголовок подключения** `<имя>_ll.h` — он компилируется в **программу** и
  состоит из таблицы указателей, функции `*_bind()` и макросов подмены имён.

Разделение именно такое, потому что это два разных мира: первый файл попадает в
`/lib/*.ll`, второй — в `.prg`.

## 3. Чем это отличается от `src/lib`

`src/lib` — общий исходный код пользовательских программ: заголовки системных
вызовов (`ovos.h`), оконный протокол (`wproto.h`), тулкит (`ui.h`/`ui.c`),
разборщики картинок (`png.h`, `bmp.h`), растеризаторы шрифта и значков
(`ttf.c`, `svg.c`), раскладки, шрифт консоли.

Правило простое:

* **`src/lib`** — код, который могут вкомпилировать в себя и программа, и
  библиотека (например, композитор `desktop.prg` компилирует `ttf.c` прямо в
  себя, потому что он рисует до того, как появятся библиотеки);
* **`src/libs/<имя>`** — то, что становится отдельным файлом `/lib/<имя>.ll`.

Поэтому `libgfx.ll` собирается из `libgfx/libgfx.c` + `src/lib/ttf.c` +
`src/lib/svg.c`: своя папка даёт «лицо» библиотеки, общий код берётся из
`src/lib`. Список исходников каждой библиотеки — в `Makefile` (`LIBGFX_SRC`,
`LIBUI_SRC` и так далее).

## 4. Как этим пользуется программа

```c
#include "ovos.h"
#include "ui.h"                  // типы и прототипы
#include "libui/libui_ll.h"      // таблица указателей + макросы

int main(void) {
    if (libui_bind() < 0) ov_exit(1);   // открыть /lib/libui.ll и найти символы
    ui_window_t* w = ui_open("Привет", 400, 300);   // вызов идёт через таблицу
    ...
}
```

`libui_ll.h` делает `#define ui_open g_ui.open`, поэтому код программы выглядит
обычно — ни одного упоминания библиотеки в самих вызовах. В makefile приложения
при этом стоит `USE_LIBUI := 1`, и `ui.o` просто не линкуется.

Проверять результат `*_bind()` обязательно: если файла нет или в нём не нашлось
символа, вернётся отрицательное число, и дальше звать функции нельзя — в
указателях нули.

## 5. `ffmpeg.ll` — порт, а не наш код

`src/libs/ffmpeg` — это порт внешней программы, как `DOOM` и `Quake` в
`src/files/progs`. Внутри не наши декодеры, а **настоящий FFmpeg 7.1**
(libavformat, libavcodec, libswscale, libswresample), собранный под overOS.

Чтобы чужой код собрался, системе понадобился «сисрут» — то, чего в overOS
никогда не было: `include/` (stdio.h, stdlib.h, string.h, math.h, time.h,
errno.h, unistd.h, fcntl.h, sys/*) и `ffsys.c`, который всё это реализует.
Рядом в ту же библиотеку линкуются `libc/libc.c` и `libm/libm.c` — то есть libc
в системе по-прежнему нет, она есть только внутри этой одной библиотеки.

`ovcc` — обёртка над gcc: `-ffreestanding -nostdinc` с нашим сисрутом, а при
компоновке наша `libffsys.a` вместо системной. Благодаря ей `./configure`
проверяет функции честно и находит ровно то, что у нас есть; всё остальное
FFmpeg подставляет своим кодом.

Собирает всё `tools/build_ffmpeg.sh` (распаковка, заплаты, конфигурация,
сборка, компоновка, упаковка в `.ll`), он же вызывается из `Makefile`.

Две тонкости, без которых не работает:

* **`--no-relax` при компоновке.** Код FFmpeg обращается к своим таблицам через
  GOT. Компоновщик, видя не-PIE выход, с удовольствием превращает такие
  обращения в абсолютные 32-битные адреса — а библиотека живёт по
  `0x6000_0000_0000`, который в 32 бита не влезает. `elf2ll.py` при этом кладёт
  каждую ненулевую ячейку GOT в таблицу релокаций: при базе 0 это обычный
  адрес внутри образа.
* **своя куча.** У FFmpeg внутри библиотеки статический пул на 40 МБ, а не
  `brk`: границу кучи процесса уже двигает `libc.ll`, и два распределителя на
  одной границе затёрли бы друг друга.

## 6. Как добавить свою библиотеку

1. Создать `src/libs/mylib/mylib.c`. Экспортируется каждая глобальная функция;
   всё внутреннее помечать `static`.
2. Ничего не импортировать: только `#include "ovos.h"` и свой код.
3. Добавить имя в `LIBS` в `Makefile` и список исходников
   (`MYLIB_SRC := $(LIBS_DIR)/mylib/mylib.c`), а затем строку
   `$(eval $(call LL_RULE,mylib,$(MYLIB_SRC)))`.
4. Написать `src/libs/mylib/mylib_ll.h` по образцу соседей: структура
   указателей, `mylib_bind()` с `OV_BIND` на каждый символ, макросы подмены.
5. В программе: `#include "mylib/mylib_ll.h"` и `mylib_bind()` в начале `main`.

## 7. Границы, о которые можно удариться

| Что | Сколько | Где задано |
| :--- | ---: | :--- |
| Образ библиотеки (код + данные) | 8 МБ | `LIB_MAX_IMAGE`, `lib_loader.h` |
| Память библиотеки (вместе с `.bss`) | 56 МБ | `LIB_MAX_MEM` |
| Слот в адресном пространстве | 64 МБ | `LIB_SLOT_SIZE` |
| Библиотек на процесс | 16 | `LIB_MAX_SLOTS` |

`ffmpeg.ll` — самая большая: 3 МБ образа и 49 МБ памяти.
